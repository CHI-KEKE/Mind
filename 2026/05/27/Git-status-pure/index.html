Git 區分狀態的底層邏輯

Git 怎麼看檔案狀態

git status 主要回答兩個問題：哪些檔案改過，以及哪些內容已經準備放進下一次 Commit。Git 會比較「已經提交的上一版」、「準備提交的版本」和「目前正在修改的版本」。

先認識三個位置

  • HEAD：已經提交的上一版。若倉庫還沒有 Commit，可以把它想成空的起點。
  • 是否已準備提交：比較 HEAD 與 Index。
  • Index，也叫暫存區：已經執行 git add，準備放進下一次 Commit 的檔案版本。
  • 是否又有新修改：比較 Index 與 Working Tree。
  • Working Tree：硬碟上目前看得到、正在修改的實體檔案。

可以把整個過程記成：在 Working Tree 修改檔案，執行 git add 把當下的版本放進 Index，最後執行 git commit 建立新的 Commit。

git status 主要整理三類資訊：

  1. 比較 HEAD 和 Index，找出已經執行 git add、準備提交的內容。
  2. 比較 Index 和 Working Tree，找出修改後還沒有執行 git add 的內容。
  3. 檢查 Working Tree，找出尚未交給 Git 管理，而且沒有被 ignore 規則排除的新檔案。

剛建立的 test.txt 只存在於 Working Tree。它還沒有執行 git add，也沒有出現在先前的 Commit，因此狀態是 Untracked。

git add 就是把內容加入暫存區

執行 git add test.txt 時，Git 會把 test.txt 當下的內容放進 Index。這個動作就叫「暫存」。檔案仍留在 Working Tree，也還沒有建立 Commit。底層會同時更新 Index 中的路徑、檔案模式與內容識別值。

Tracked、Untracked 與 Ignored

Tracked 表示檔案已經交給 Git 管理。它可能早已存在於某個 Commit，也可能是剛執行 git add、第一次放進 Index 的新檔案。

Untracked 表示這是尚未執行 git add 的新檔案。檔案存在於 Working Tree，但上一個 Commit 與 Index 都沒有它。

只有 Git 尚未追蹤的路徑，才會繼續套用 .gitignore 等 ignore 規則。已追蹤的檔案不會因為後來加入 .gitignore 就自動停止追蹤。

  1. 這個路徑已被 Git 追蹤？
  2. 是：Tracked。再比較三個位置，判斷最新修改是否已經執行 git add。
  3. 否：符合 ignore 規則？
    • 是：Ignored，一般的 git status 不列出。
    • 否：Untracked，列在未追蹤檔案中。

ignore 實驗觀察

這個實驗先建立 test.txt，再把它寫進 .gitignore。因為 test.txt 從未執行 git add，Git 還沒有開始追蹤它，所以 ignore 規則可以把它隱藏起來。

  1. 建立倉庫：git init 建立空倉庫，此時還沒有 Commit，也沒有被追蹤的檔案。
  2. 建立 test.txt：檔案只存在於 Working Tree，所以 git ls-files 沒有輸出。
  3. 加入 ignore 規則：.gitignore 符合 test.txt，一般的 git status 不再列出它。
  4. 顯示 ignored 檔案：git status --ignored 會把 test.txt 顯示在 Ignored files 區段。

建立順序不是關鍵

先建立 .gitignore 再建立 test.txt，結果也相同。判斷重點是 test.txt 尚未執行 git add，也沒有出現在先前的 Commit。

狀態

Git 判斷狀態時，可以分成兩個問題。第一個問題是「Git 是否已經知道這個路徑」，第二個問題是「三個位置之間是否有差異」。

第一個問題：Git 是否管理這個路徑

  • Tracked：Git 已經在管理這個檔案。它曾經被 Commit，或已透過 git add 放進 Index。
  • Untracked：尚未執行 git add 的新檔案，Git 還沒有開始管理它。
  • Ignored：路徑尚未被追蹤，而且符合 ignore 規則。一般的 git status 不會列出它。

第二個問題：三個位置是否有差異

狀態 Git 看到的差異 代表意思
Unmodified 三個位置的內容一致 Git 正在管理檔案，目前沒有變更
Modified Working Tree 與 Index 不同 檔案已修改，但最新內容尚未執行 git add
Staged Index 與 HEAD 不同 已執行 git add，這個版本會進入下一次 Commit

Staged 與 Modified 可以同時存在

假設檔案的 A 版本先執行 git add，接著又改成 B 版本。Index 裡仍是準備提交的 A 版本，Working Tree 則是最新的 B 版本。若沒有再次執行 git add，下一次 Commit 只會收錄 A 版本。

已經被 tracked 才加入 ignore file 實驗

這個實驗先對 tracked.txt 執行 git add。這時檔案已放進 Index，Git 也開始追蹤它。之後才把相同路徑加入 .gitignore，無法取消已經開始的追蹤。

  1. 建立 tracked.txt：檔案剛建立時仍是 Untracked。
  2. 執行 git add：tracked.txt 的當下版本放進 Index，成為 Tracked 與 Staged。
  3. 寫入 .gitignore：ignore 規則只影響尚未追蹤的路徑，不會刪除 Index 裡既有的項目。
  4. 再次執行 git status：tracked.txt 仍出現在 Changes to be committed。

.gitignore 不會解除追蹤

tracked.txt 已經透過 git add 放進 Index，因此 Git 仍準備把它放進下一次 Commit。若要保留本機檔案，但不再讓 Git 追蹤，需要使用 git rm --cached。

git rm –cached

git rm --cached tracked.txt 會把 tracked.txt 從 Index，也就是 Git 準備提交與追蹤的清單中移除，但不會刪除硬碟上的實體檔案。

  • 執行前
    • Index 有 tracked.txt
    • Working Tree 有 tracked.txt
  • 執行 git rm --cached tracked.txt
  • 執行後
    • Index 移除 tracked.txt
    • Working Tree 保留 tracked.txt

與一般 git rm 的差別

指令 從 Index 移除 刪除硬碟檔案 適用情境
git rm --cached <檔名> 是 否 停止追蹤，但保留本機檔案
git rm <檔名> 是 是 從版本控制與工作目錄一起移除檔案

實驗

為什麼這次沒有出現 deleted

這個實驗還沒有建立任何 Commit，所以 HEAD 是空的。把 tracked.txt 從 Index 移除後，準備提交的內容也變回空白，因此沒有顯示刪除。若檔案早已存在於先前的 Commit，執行 git rm --cached 會把「下一次 Commit 要停止追蹤這個檔案」列為已暫存的變更。

為甚麼會有 Staged 階段

Working Tree 裡可能同時存在已完成、做到一半與只供測試的修改。若 git commit 每次都收錄全部修改，不相關的內容就會混進同一個版本存檔點。Staged 階段讓 Git 多一個「先挑選，再存檔」的步驟。

  • Working Tree：目前所有修改，包含完成與尚未完成的內容。
  • git add 挑選
  • Index，也叫暫存區：這次準備提交的內容，可以把它看成下一個 Commit 的草稿。
  • git commit 存檔
  • Commit：把 Index 的內容正式保存成一個版本存檔點。

同時修改三個檔案的例子

目前有三個檔案發生異動，但這次只想提交已完成的登入修正：

檔案 目前情況 這次是否執行 git add 是否進入下一個 Commit
login.cs 登入修正已完成 是 是
payment.cs 付款功能做到一半 否 否，繼續留在 Working Tree
notes.txt 本機測試紀錄 否 否，繼續留在 Working Tree

這次 Commit 只收錄 login.cs。另外兩個檔案不會消失，也不會被提交，仍然留在 Working Tree。

同一個檔案也能只挑部分修改

git add -p login.cs 會把修改拆成數個區塊，再逐一決定是否放進 Index。因此 Staged 挑選的不只是檔名，也可以是檔案裡的部分修改。

Staged 階段的目的，是讓每個 Commit 只保存一組彼此相關、已經準備好的修改。這樣比較容易閱讀歷史、進行 Code Review，也比較容易只還原某一次修改。

commit 的意義

Commit 可以理解成 Git 裡的一個「版本存檔點」。它會保存 Index 當下準備好的內容，並接在前一個 Commit 後面，形成可以回頭查看的版本歷史。

  1. Commit A：建立專案的最初版本。
  2. Commit B：在 Commit A 後面加入登入功能。
  3. Commit C：在 Commit B 後面修正登入錯誤。

每個 Commit 都是獨立的版本存檔點，因此可以查看某個版本、比較兩個版本，或把檔案恢復成某個版本的內容。

一個 Commit 記錄哪些資料

資料 代表意思
專案快照 這次 Commit 保存的檔案與目錄內容
上一個 Commit 這個版本是接在哪個版本後面
作者與時間 誰在什麼時間建立這個版本
Commit Message 這次修改的說明，例如「修正登入錯誤」
Hash 辨識這個 Commit 的編號，例如 a1b2c3d

Commit 同時是動作與結果

  • 作為動作：執行 git commit，把 Index 的內容保存成一個新版本。
  • 作為結果：指已經建立好的版本紀錄，例如「查看上一個 Commit」。

Commit 不等於上傳

  • git add：挑選內容，放進 Index。
  • 準備完成
  • git commit：在本機建立版本存檔點。
  • 需要分享時
  • git push：把本機 Commit 上傳到遠端倉庫。

Commit 建立後，內容就固定了

Commit 會依專案快照、上一個 Commit、作者、時間與說明等資料產生自己的 Hash。即使使用 git commit --amend 修改上一個 Commit，Git 實際上也是建立另一個新 Commit，並產生新的 Hash。

所以 git commit -m "修正登入錯誤" 的完整意思是：把 Index 裡準備好的內容，在本機建立成一個新的版本存檔點，並用「修正登入錯誤」說明這次修改。
