二補數：把減法偽裝成加法的把戲

CPU 裡其實只有一顆加法器，卻能算出減法、算出負數。祕密就藏在一段固定的位元轉換規則裡。

Two’s Complement Signed / Unsigned Integer Overflow

>_

為什麼需要二補數

電路設計上，CPU 真正負責四則運算的硬體只有一顆加法器，並沒有天生內建的減法電路。如果只支援正數的加法，那麼要處理「減法」與「負數」，就變成一項額外的需求。設計上大致只有兩條路：另外造一顆專門的減法電路，或是想辦法讓負數本身也能透過同一顆加法器直接被算出正確答案。

後者聽起來比較划算，但要成立必須先解決一個問題：負數在位元層面該怎麼表示，才能讓現有的二進位加法器不需要任何修改，直接把結果加出來就是對的。

一個直覺但行不通的做法

如果直接用「符號位加大小」的方式表示負數，也就是最高位當作正負號，其餘位元照原本的大小表示，例如 -5 表示成 1000 0101（最高位 1 代表負，其餘 000 0101 是 5），拿去跟 5 = 0000 0101 做一般的二進位加法：

naive.sim 
  0000 0101   // 5
+ 1000 0101   // 符號位+大小表示的 -5
-------------
  1000 1010   // 按同一套規則解讀 = -10

加法器完全不知道最高位是特殊的符號位，只是照一般規則把每一位加起來，得到的 1000 1010 若照同一套解讀方式，會被念成 -10。但數學上 5 + (-5) 應該是 0，結果完全錯誤。這代表「符號位加大小」這種表示法沒辦法直接套用一般的二進位加法器，必須額外判斷符號位、另外處理進位，等於還是要多一套邏輯。

需要負數
→
符號位+大小表示法
→
一般加法器算出錯誤答案
→
還需要另一套規則
!

真正的需求：必須找到一套負數的位元表示規則，讓現有的二進位加法器完全不用修改，直接把兩個數字的 bits 加起來，就能得到正確答案。這正是二補數要解決的問題。

在拆解二補數實際怎麼算之前，先建立一個更基礎的概念：同一串 bits 該怎麼被解讀成數字，也就是接下來要談的 signed 與 unsigned。

>_

Signed 與 Unsigned

signed 跟 unsigned 其實是在告訴電腦：「同一串 bits，要用哪一套規則解讀成數字」。unsigned 把全部空間都拿來表示 0 和正數，signed 則通常採用二補數規則，讓同樣的 bits 可以同時涵蓋負數、0、正數。

8 bit 樣式 signed 二補數解讀 備註
1111 1111 -1 定義起點
1111 1110 -2 比 -1 再倒退一格
1000 0001 -127 逼近最負值
1000 0000 -128 signed 8 bit 能表示的最負值
0000 0000 0 零點
0111 1110 126 逼近最大正數
0111 1111 127 signed 8 bit 能表示的最大正數

同一串 bits 1111 1111 到底是多少

若用 unsigned 解讀，這串 bits 是 255；若用 signed 二補數解讀，同一串 bits 卻是 -1。bits 本身完全沒有改變，改變的只是解讀規則。

i

本質：signed / unsigned 其實就是一份「bit pattern 對應到數值」的解讀規則，ALU 算出來的 bits 完全相同，但程式認為它代表多少，會因為 signed 或 unsigned 而不同。

假設記憶體裡真的存著 1111 1111，硬體本身看到的就只有這 8 個 bits，它並沒有額外標記「這是 -1」或「這是 255」，要看使用哪種型別去解讀。

那麼問題來了：signed 二補數這份解讀規則，實際上是怎麼從一個正數推出對應的負數表示的？接下來就是二補數真正的計算規則。

>_

二補數怎麼算：反轉再加 1

二補數的規則很固定：把一個正數的每一位反轉，再加 1，就能得到它對應的負數表示。以 5 為例：

negate.sim 
5       = 0000 0101
反轉     = 1111 1010
+1      = 1111 1011

所以 -5 = 1111 1011。接下來驗證這個結果是否成立，把 5 跟這個 -5 相加：

alu.sim 
  0000 0101   // 5
+ 1111 1011   // -5
-------------
1 0000 0000

因為暫存器只有 8 bit，最左邊多出來的那個 1 會被直接丟掉，只留下 0000 0000，也就是 0。5 + (-5) = 0 完全正確，而且從頭到尾只用了同一顆加法器，沒有另外造任何減法電路。

5 + (-5)
→
最高位多出一個 1
→
超出 8 bit 直接捨去
→
結果 = 0

減法也能套用同一套邏輯

例如 5 - 3 可以先轉換成 5 + (-3)，一樣先用「反轉再加 1」找出 -3：

negate.sim 
3       = 0000 0011
反轉     = 1111 1100
+1      = 1111 1101

所以 -3 = 1111 1101，接著把 5 跟 -3 相加：

alu.sim 
  0000 0101   // 5
+ 1111 1101   // -3
-------------
1 0000 0010

留下 8 bit 之後是 0000 0010 = 2，所以 5 - 3 = 2，答案完全正確。

✓

核心概念：二補數的本質，就是想辦法把「減法問題」轉換成 CPU 原本就很擅長的「加法問題」，讓硬體不用多長一顆專門處理減法的電路。

為什麼偏偏是「反轉再加 1」

反轉每一個位元，其實只能幫忙算到 255 - x，但要湊出負數真正需要的是 256 - x，所以最後差的那個 1，就是靠額外加 1 補上去的。

1
目標：找出讓 5 歸零繞回的那個數

已知 5 = 0000 0101，希望找到一個值 ?，使得 5 + ? = 256，所以 ? = 256 - 5 = 251。

2
但「反轉 5」實際上只算出 255 - 5

因為 1111 1111 = 255，把每一位反轉等同於用 255 去減，反轉後的值是 250，離目標的 251 還差 1。

3
補上那差的 1

反轉 + 1 = 250 + 1 = 251，正好等於 256 - 5，也就是二補數表示法裡的 -5。

proof.sim 
  1111 1111  // 255
- 0000 0101  // 5
-------------
  1111 1010  // 反轉結果 = 255 - 5 = 250

整理成一個關係式：反轉 + 1 = (255 - x) + 1 = 256 - x。

為什麼偏偏要湊到 256

因為 8 bit 只能保存 0 ~ 255 這個範圍，一旦數值來到 256，二進位會變成 1 0000 0000，超出的最高位放不下，只留下 8 bit 的 0000 0000，等於 256 會直接繞回 0。這正是能夠成立 5 + (-5) = 5 + 251 = 256，而 8 bit 只留下 0000 0000，也就是 0 的原因。

i

換一個位元寬度驗證：如果是 4 bit（2^4 = 16），要表示 -5 就要湊到 16 - 5 = 11。

4bit.sim 
5  = 0101
反轉 = 1010      // 10
+1  = 1011      // 11
4bit.sim 
  0101   // 5
+ 1011   // -5
------
1 0000   // 只保留 4 bit 之後 = 0000

所以「二補數反轉再加 1」可以記成一條固定的因果鏈：

N bit 在 2^N 會繞回 0
→
-x 需要湊到 2^N - x
→
反轉只能得到 2^N - 1 - x
→
還差 1
→
所以要 +1
>_

Integer Overflow

signed 與 unsigned 的可表示範圍不同，所以同一個位元運算，可能對 signed 而言已經溢位，對 unsigned 卻完全正常。以 8-bit signed 為例，它裝不下 128，留下來的 1000 0000 按 signed 二補數規則會被解讀成 -128。

!

Overflow 發生後：真正的數學答案沒有被完整保留下來。ALU 會留下低位的 N bits，並額外產生一個 overflow 訊號，後續要怎麼處理，交由 CPU 指令、程式語言或程式本身決定。

1
ALU 照樣完成位元加法

ALU 不會因為數值看起來偏大就拒絕運算，它仍然完成 0111 1111 + 0000 0001 這組位元加法，得到 1000 0000。

2
結果的 bits 被錯誤解讀

把 1000 0000 以 8-bit signed 二補數解讀，會得到 -128。但數學上真正的答案是 127 + 1 = 128，這個 -128 已經無法代表真正的答案。

3
ALU 同時偵測到 overflow

ALU 除了輸出 Result，通常還會同時產生 Overflow = 1 這個狀態訊號，意思是「若把這次運算當成 signed integer，Result 已經無法正確表示真正答案」。

alu.diagram 
              ALU
        +--------------+
127 --->|              |---> Result = 1000 0000
  1 --->|    Adder    |
        |              |---> Overflow = 1
        +--------------+

可以把 Result 和 Overflow 看成兩份不同的資訊：Result 回答「這次硬體算完，留下哪些 bits」，Overflow 回答「這些 bits 還能不能正確代表 signed 數學上的答案」。

01 10 01

真實案例 Ariane 5 首飛失敗（1996）

1996 年 6 月 4 日，European Space Agency 的 Ariane 5 火箭首次飛行，在升空大約 37 秒後失去導引資訊，偏離航線，最終解體並自毀。ESA 的調查指出，問題鏈條源自慣性參考系統的軟體設計，其中涉及數值轉換時發生的 operand error。

最值得注意的地方在於，程式把一個較大範圍的數值塞進較小範圍的整數表示，實際數值超出目標型別能表示的範圍後觸發例外，而錯誤處理與備援設計又讓問題一路擴散到飛行控制。這跟前面提到的「8-bit signed 只能表示 -128 到 127」是同一類核心問題，只是 Ariane 5 實際系統的資料型別與軟體流程遠比 8-bit 範例複雜。

可以先用熟悉的 8-bit 假想版本理解這個問題。假設有一個較大的數值 velocity = 200，硬要把它放進 8-bit signed，但 8-bit signed 只能表示 -128 ~ 127：

velocity = 200
→
想塞進 signed 8-bit
→
最大只能到 127
→
超出可表示範圍
→
Overflow / conversion error

Ariane 5 的實際問題涉及把 64-bit 浮點值轉換成 16-bit signed integer，其中一個轉換值超出了 16-bit signed integer 能表示的範圍，引發 operand error。調查報告還指出，相關保護沒有覆蓋這個變數，因為設計時認為它在預期操作範圍內不會出問題。

1
數值超出目標整數範圍

數值轉換發生 operand error，觸發軟體 exception。

2
慣性參考系統停止正常工作

備援系統遇到相同的轉換問題，也一併失效。

3
飛行器失去有效導引與姿態資訊

控制系統收到異常資訊，噴嘴大幅偏轉。

4
結構解體、自毀

火箭急劇偏離航線，結構承受巨大空氣動力負載，最終解體並觸發自毀。

ESA 的正式調查確認，兩套慣性參考系統幾乎同時失效，最終造成導引與姿態資訊完全喪失。

  • ALU 永遠會把運算算完，不會因為數值「看起來太大」就自動停下來
  • overflow 是額外的狀態訊號，真正要不要處理，取決於上層程式或硬體保護機制
  • 把大範圍數值硬塞進小範圍整數型別，是實際系統中真正發生過重大事故的根因之一
