Bounded Queue

Created2026-09-13|Updated2026-09-14|CS
|Post Views:
Concurrency · Backpressure

當資料來得比處理速度快

有界佇列把等待中的資料量限制在可預測範圍內。系統必須在排隊、拒絕、丟棄或阻塞之間做出明確選擇，才能避免短暫流量把整台服務拖垮。

容量有限背壓可見失敗策略明確
01

什麼時候需要 Bounded Queue

觸發情境 沒有容量邊界時 Bounded Queue 的作用 必須接受的代價
供需速率嚴重不對稱 前端 API 閘道器每秒湧入 50,000 筆請求，但後端資料庫每秒最多只能寫入 3,000 筆，等待資料持續增加。 搭配 Kafka 的非同步削峰填谷，也就是 Asynchronous Write 或 Queue based Load Leveling，暫時吸收上游與下游的速率落差。 使用者點完按鈕後無法立刻在資料庫看到結果，必須等待系統非同步消化完畢。佇列只能吸收短期尖峰，不是永久產能。
預防 OOM 雙 11、跨年、股市開盤、搶票，或下游第三方 API 變慢時，無界佇列持續成長，可能造成 OutOfMemoryError。 固定容量限制等待中的資料，讓記憶體上限、滿載行為與失敗範圍可以事先定義。 容量到頂後仍必須拒絕、丟棄、阻塞或持久化，無法同時保留所有資料並維持無限流量。
外部服務有頻率限制 黑貓物流 API、金流刷卡閘道、Twilio 簡訊與 OpenAI API 可能限制每秒呼叫 100 次，超過就鎖 IP、罰款或直接報錯。 建立固定大小的佇列，由固定數量的執行緒，例如 10 個 Worker，依序取出任務呼叫外部 API。 超過處理能力的請求需要等待或被拒絕，不能讓所有請求立即通過。
💡

核心界線：入列成功只代表資料進入等待區，不代表資料已經寫入資料庫。若需要讓使用者立即知道永久寫入結果，就不應只用非同步佇列取代同步確認。

02

容量用盡時的處理策略

以下是彼此獨立的滿載處理策略，不是依序執行的步驟。實際系統會依資料是否可丟失，以及業務是否能接受等待來選擇。

flowchart TB Root([佇列已滿]) –> Q1{資料不能丟失？} Q1 –>|是| Q2{業務可以等待？} Q2 –>|是| A[阻塞上游，形成背壓] Q2 –>|否| B[轉交持久化訊息系統] Q1 –>|否| Q3{只需要最新資料？} Q3 –>|是| C[丟棄舊資料或低價值資料] Q3 –>|否| Q4{上游可以重試？} Q4 –>|是| D[拒絕新資料並快速回報] Q4 –>|否| E[重新檢視業務承諾與資料優先級]

03

不一定要排隊的替代方案

方案 適用條件 主要代價
Write Back 快取 可接受資料先存在 Redis 或其他快取，稍後批次寫入資料庫。 快取故障、批次尚未落盤或重複寫入時，需要額外的可靠性設計。
資料庫分片 資料可以依使用者 ID、設備編號等穩定 Key 分散到多個資料庫。 跨分片查詢、交易與資料重新分布都會增加複雜度。
Load Shedding 請求有清楚的優先級，低價值資料可以被捨棄。 被捨棄的資料無法靠佇列補回，業務必須接受降級結果。
同步處理與擴充 結果必須立即確認，且流量可透過更多處理節點或更快的儲存系統承接。 硬體、資料庫授權與維運成本上升，擴充也可能有上限。
💡

選擇方式：先比較資料能不能延後、資料能不能丟、下游能不能水平擴充。若三個答案都是否定，系統需要重新檢視業務承諾，單靠佇列無法消除容量矛盾。

Write Back 的批次寫入

資料庫寫入慢，可能是因為硬碟 I/O 成本高。前端的 50,000 筆請求可以先直接寫入 Redis 或記憶體資料庫，寫入成功後立刻回傳使用者。後台再每隔 1 秒把累積的幾萬筆資料打包成巨大的 INSERT，使用 Batch Insert 一次寫入資料庫。

對資料庫來說，逐筆寫入與一次批次寫入 10,000 筆資料的磁碟尋道成本可能接近。這種方式能大幅降低資料庫負擔，但必須處理快取故障與資料尚未落盤的風險。

Sharding 的數量級推導

假設單一資料庫每秒只能承受 3,000 筆寫入，可以依使用者 ID 或 IoT 設備編號進行分片。ID 尾數為 0 到 9 的資料送往 A 資料庫，10 到 19 的資料送往 B 資料庫，以此類推，共使用 20 台資料庫獨立運作。

原本單台每秒 3,000 筆，20 台並行後，整個叢集的寫入能力約為 3,000 × 20 = 60,000 筆／秒，理論上可以承接每秒 50,000 筆流量。這條路徑不需要讓使用者排隊，但會增加跨分片查詢、交易與資料重新分布的複雜度。

遊戲系統的主動捨棄

即時系統的 50,000 筆請求可能包含玩家移動座標、玩家聊天與玩家買裝備。當資料庫處理速度跌破警戒線，閘道器可以啟動 Load Shedding，捨棄 80% 的玩家移動座標，只保留買裝備與聊天。

若前端過濾後只剩 2,500 筆送往資料庫，核心業務可以繼續運作，但被捨棄的座標資料無法靠佇列補回。

04

無界佇列為什麼可能造成更大損失

無界佇列把等待資料放在程序記憶體中。當輸入速度長時間高於處理速度，佇列會持續成長，最後可能觸發 OutOfMemoryError。程序被終止後，尚未持久化的資料也會跟著消失。

起點輸入速度持續高於處理速度

等待中的任務逐漸增加，記憶體使用量跟著上升。

壓力升高記憶體壓力擴大

垃圾回收更頻繁，處理速度可能進一步下降，形成惡性循環。

故障點程序被迫終止

程序崩潰或被作業系統終止後，記憶體中的等待資料沒有持久化副本。

程序終止後的流量分支

程序被終止後，結果取決於負載平衡器是否把流量轉移到其他節點。

flowchart TB Stop[程序被終止] –> Lost[尚未持久化的等待資料遺失] Stop –> Route{負載平衡器轉移流量？} Route –>|否| Isolated[單一節點受影響] Route –>|是| Overflow[其他節點承受額外流量] Overflow –> Repeat[無界佇列持續成長] Repeat –> Cascade[連鎖 OOM，形成雪崩]

無界佇列的風險不只是一批資料遺失。當一台伺服器因 OOM 當機，負載平衡器可能把原本分配給它的流量轉移到其他健康節點。其他節點若也使用無界佇列，就可能一台接一台被撐爆，形成雪崩。

在斷電或程序暴斃的幾個小時內，核心服務可能完全無法提供，丟失的資料量與商業損失可能遠高於採用明確 Drop Policy 的有界佇列。

05

標準庫裡的有界佇列

語言 常見工具 容量設定
Java ArrayBlockingQueue、LinkedBlockingQueue 建立佇列時指定容量
Go make(chan Type, capacity) 建立帶容量的 Channel
C# System.Threading.Channels、BlockingCollection 依 API 設定 bounded capacity
Python queue.Queue(maxsize) 以 maxsize 設定上限
C++ 標準容器通常不直接提供執行緒安全的 bounded queue 需由應用程式或第三方函式庫補上同步與容量策略

C++ 的 STL 預設容器通常是無界的，但 Boost 等高效能函式庫，以及 Meta、Google 等科技公司的開源函式庫，都能找到專用的 BoundedQueue 實作。

06

作業系統與網路中的有界緩衝區

有界佇列不只存在於應用程式。網卡接收區、核心 Socket Buffer、資料庫連線池，都會用固定或可設定的容量限制資源使用量。

封包穿過多層有界緩衝區

閱讀方向由上往下。每一層都是容量有限的等待區，處理速度跟不上時，封包會在該層被捨棄或讓上游降低速度。

flowchart TB NIC[網卡硬體] –> RX[RX Ring Buffer] RX –>|DMA 寫入| IRQ[Hard IRQ / SoftIRQ] IRQ –> NAPI[NAPI 驅動處理] NAPI –> SKB[sk_buff] SKB –> Stack[IP / TCP / UDP 協議棧] Stack –> Socket[Socket Receive Buffer] Socket –> App[“應用程式 read() / recv()”]

硬體接收區與核心搬運

網卡可透過 DMA 把封包寫入固定大小的 RX Ring Buffer。Ring Buffer 的長度通常在系統啟動或驅動程式載入時固定，例如常見的 512 或 1024 個插槽。網卡填入封包後會向 CPU 發出 Hard IRQ。

若 CPU 忙於昂貴運算或頻繁上下文切換，SoftIRQ 可能無法及時執行驅動程式的 poll()，搬運工作就會延遲。當 RX Ring Buffer 沒有可寫入的 Descriptor，網卡硬體會直接拒絕新封包。在 Linux 中，這類情況可能反映在 rx_fifo_errors 或 overruns 計數器。

核心再透過 NAPI 與 SoftIRQ 將封包交給協議棧，封裝成 sk_buff，最後放進應用程式的 Socket Receive Buffer。

Socket 滿載時的 UDP／TCP 分支

若應用程式沒有及時執行 read() 或 recv()，Socket 接收緩衝區也會到達上限。可透過 Linux 的 net.core.rmem_max 設定接收緩衝區上限。

flowchart TB Full[Socket Receive Buffer 已滿] –> Protocol{傳輸協議？} Protocol –>|UDP| UDPDrop[“kfree_skb()，新封包被捨棄”] Protocol –>|TCP| TCPWindow[“縮小接收 Window 或送出 Zero Window”] TCPWindow –> Sender[“發送端降速或重傳”]

UDP 與 TCP 的差異

UDP 沒有連線層的重傳與流量控制，接收緩衝區滿載時，新封包可能直接被捨棄。TCP 則透過接收視窗通知發送端降低傳送量，並在偵測到遺失時依協議進行重傳。若發送端遇到遺失，通常會等待數百毫秒後重傳，並依擁塞控制降低傳送速度，因此使用者可能感受到 Lag 與吞吐量下降。

07

資料庫連線池也是容量邊界

資料庫的容量限制通常同時出現在資料庫端與應用程式端。兩者都有限，錯誤訊息可能相似，但處理責任不同。

位置 容量邊界 滿載結果
MySQL max_connections 與每條連線需要的執行緒、記憶體資源 新連線可能收到 Too many connections
應用程式連線池 例如 HikariCP 的最大連線數與等待逾時 等待超過 Connection Timeout 後拋出連線取得失敗 
[應用程式執行緒]
        │ 取得連線
        ▼
[有限容量的等待區]
        │ 等待可用連線
        ▼
[連線池，最大 10 條]
        │ SQL
        ▼
[MySQL，max_connections 有上限]
🔎

閱讀方式：連線池的等待上限保護資料庫，也保護應用程式執行緒。等待逾時不是資料庫成功處理的證明，而是應用程式在期限內拿不到資源的結果。

假設微服務有 100 個執行緒，連線池大小固定為 10。突發流量進來時，前 10 個執行緒取得連線，剩下的 90 個執行緒進入等待區。若等待區的 Connection Timeout 設為 30 秒，超過期限仍拿不到連線的執行緒就會被移出，程式可能拋出 SQLTransientConnectionException: Connection is not available, request timed out after 30000ms。

寧可讓前端網頁逾時，也不要讓 100 個甚至 1,000 個連線同時湧入 MySQL。資料庫若因 CPU 使用率達到 100% 或資源競爭陷入 Deadlock，整個系統可能徹底癱瘓。

08

Token Bucket 與 Bounded Queue 的關係

Token Bucket 以固定速率 r 產生令牌，桶子的容量為 B。請求進來時先取得令牌，有令牌就能通過，沒有令牌則拒絕或回傳 HTTP 429。 

[令牌產生器，每秒產生 r 個]
              │
              ▼
[Token Bucket，容量 B]
       │ 有令牌       │ 無令牌
       ▼              ▼
[放行請求]       [拒絕或回傳 429]
✅

關鍵差異：一般 Bounded Queue 儲存等待中的工作，Token Bucket 儲存可用額度。前者控制待處理資料量，後者控制一段時間內允許通過的流量。

當系統平時流量很低，桶子會累積令牌，最多累積到 B 個。突然有 5,000 筆請求湧入時，桶中的令牌可以讓一批請求在極短時間內通過，直到令牌耗盡才開始嚴格限流。桶子已滿時，新產生的令牌會自動作廢，而不是無限累積。

因此 Token Bucket 的重點是讓系統在安全上限內保有 Burstiness 彈性，不是把所有請求排進等待佇列。

09

設計時的檢查清單

  • 容量是依記憶體、延遲、下游處理速度，還是業務可接受等待時間推導出來的？
  • 佇列滿載時要拒絕、丟棄、阻塞，還是轉存到持久化訊息系統？
  • 上游是否能辨識入列成功與業務完成的差異？
  • 重試是否有上限、退避策略、冪等處理與死信位置？
  • 是否監控佇列深度、等待時間、拒絕數、丟棄數與 Consumer 速度？
  • 尖峰持續超過下游產能時，系統是否仍有可預期的降級結果？
Bounded Queue 的重點不是讓所有資料永遠等待，而是讓系統在資源不足時仍保持可預期。
