監控基礎架構

Created2026-09-22|Updated2026-09-25|Metric
|Post Views:

架構

從數字找到異常，從紀錄追查原因

凌晨收到服務錯誤通知時，先確認影響範圍與開始時間，再查看當時留下的事件紀錄。監控架構把這兩種資料接到同一個觀察介面。

收到 API Error Rate > 5% 通知之後

調查方向 具體問題 資料來源
觀察趨勢 目前錯誤多不多？從什麼時候開始？哪一台 Pod 特別嚴重？ Prometheus 的 Metrics
追查細節 到底報什麼錯？哪個 endpoint？Exception 是什麼？Request ID 是多少？ Loki 的 Logs

Grafana 將這兩條調查路線接在同一個介面。能否依服務、Pod 或 Request ID 對照，仍取決於實際收集的指標 Labels、Log 欄位及資料來源設定。

metric

讓數字帶上觀測上下文

同樣是 100，單獨看只能知道數量。加上指標名稱、分類與觀測時間後，才知道哪個服務發生了什麼變化。

Metric 與一般數值

metric 是單數，例如「CPU 使用率這個 metric」；metrics 是複數，也常泛指監控指標資料。Metric 是量化系統狀態或行為的指標，觀測時會連同對象、時間與分類資訊一起解讀。

核心仍是數字，例如 80、512、1000、0.52。有了上下文，才可以回答「誰、什麼時候、屬於哪一類，以及如何變化」。一般變數也能保存數值，但是否成為可持續查詢的監控資料，取決於後續的量測、暴露與收集流程。

程式內的一般變數

程式結束後，這個變數可能跟著消失。若要監控 order-api 收到多少 Request，可以透過指標暴露累計數量。

帶有名稱的指標樣本

Labels 是可組合的分類維度

系統可能同時提供 GET /users、POST /orders、GET /products。加入 Labels 後，同一個指標名稱可以描述不同請求類別。

指標名稱、Labels 與樣本值

組成 範例 意義
指標名稱 http_requests_total 記錄 HTTP 請求累計數
Labels method="POST"、path="/orders"、status="200" 共同識別同一組分類
樣本值 100 該組分類在觀測時的累計值

指標名稱與完整 Label 集合共同識別一條時間序列。Prometheus 保存該序列的時間戳記與樣本值。參考 Prometheus 資料模型。

另一組分類的樣本

分類維度 可觀察的值 關係
Method GET、POST 依請求方法篩選
Status 200、404、500 依回應狀態篩選
Pod api-01、api-02 依執行實例篩選

Method、Status 與 Pod 是不同維度，可以同時套用條件。例如查詢 api-01 中狀態為 200 的 GET 請求。它們不是互斥的樹狀分支。

同一條時間序列，持續累積樣本

以 method="POST", path="/orders", status="200" 這組 Labels 為例，Prometheus 定期取得下列樣本。

橫軸是時間，縱軸是請求累計數；折線只連接示例樣本，不代表已知兩次抓取之間的每一筆請求。

  • 最近增加多快？
  • 最近 5 分鐘有多少 Request？
  • 今天與昨天差多少？
  • 哪個 Pod 的 Request 最多？
  • 500 Error 的比例是多少？

原始量測與衍生指標

Pod 記憶體可以直接以 container_memory_working_set_bytes 表示。這接近原始量測（raw measurement）的用途，但 working set 本身仍是監控元件依底層資訊定義的量測值。

記憶體樣本：1,572,864,000 bytes

時間 Memory 顯示示例
08:00 1.2 GB
08:01 1.3 GB
08:02 1.5 GB

上述時間表是一組獨立的顯示示例，不是把同一筆 1,572,864,000 bytes 重複換算。資料從真實系統的量測產生 Metric，再經計算或聚合形成衍生指標或查詢結果，最後由 Grafana 顯示。

記憶體換算：bytes、GiB 與使用率

flowchart TB
Raw["Container 量測：1,800,000,000 bytes"] -->|原始 bytes| Convert["除以 1024 的三次方"]
Convert -->|約 1.6764 GiB| Display["顯示值：1.68 GiB"]
Display -->|除以 Limit，再乘以 100| Ratio["顯示值算例：84%"]
Limit["Memory Limit：2 GiB"] -->|提供分母| Ratio

由上往下讀，箭頭表示數值轉換與計算輸入。以顯示值計算，1.68 ÷ 2 × 100 = 84%；使用未四捨五入的原始 bytes 計算則約為 83.82%。1.68 GiB 與 84% 都能作為觀察指標。

GB 與 GiB 不同：1 GB = 10⁹ bytes，1 GiB = 1024³ bytes。原稿的 GB 顯示例與這裡的 GiB 換算例分開使用。Memory Used 以此處的 working set 為例，實務上仍須確認儀表板採用的記憶體定義。

Counter 經 rate() 轉成每秒速率

時間 http_requests_total 累計值 rate() 結果示意
08:00 10000 8 req/s
08:01 10600 10 req/s
08:02 11500 13 req/s

查詢最近 5 分鐘的平均每秒增長率

http_requests_total 是累加型 Counter，rate() 將時間窗內的樣本轉成平均每秒速率，並處理 Counter reset。右欄的 8、10、13 req/s 保留作為輸出形式示意；單靠左欄三筆資料，無法計算完整 5 分鐘視窗的這些結果。參考 Prometheus rate() 定義。

Prometheus

分清楚量測與抓取的責任

底層元件先取得系統資訊並暴露指標，Prometheus 再定期抓取、保存與查詢。知道數字從哪裡來，才能判斷儀表板正在觀察什麼。

Prometheus 的起源與角色

Prometheus 是用於收集、保存與查詢系統 Metrics 的開源監控系統。Matt T. Proud 與 Julius Volz 在 2012 年於 SoundCloud 啟動專案；2016 年加入 CNCF，成為 Kubernetes 之後第二個託管專案，2018 年畢業。參考 Prometheus 專案發起者與 CNCF 畢業公告。

例如監控元件提供 container_memory_working_set_bytes，樣本值為 1800000000，也就是十進位的 1.8 GB。暴露格式應使用 bytes 數值，不直接在樣本後面寫 1.8GB。

四種主要 Metric 型別

型別 觀察方式 範例與限制
Counter 持續累加，重啟等情況可能重設 Request 總數、Error 總數；通常搭配 rate() 或 increase()。
Gauge 可以增加，也可以減少 Memory、在線人數、已計算的 CPU 使用率；CPU 累計使用秒數則通常是 Counter。
Histogram 觀察大量事件的分布 例如 Request 耗時。Classic Histogram 使用累積 bucket，查詢端可計算 quantile。
Summary 記錄觀測總數、總和，並可輸出用戶端計算的 quantile 例如 Request 耗時；不同實例的 quantile 不能直接相加或平均成整體 quantile。

「0–100 ms 有幾次、100–500 ms 有幾次」是在問區間分布。Classic Histogram 的 le="0.1" 表示不超過 100 ms 的累計次數，le="0.5" 表示不超過 500 ms；兩者相減才能得到大於 100 ms、且不超過 500 ms 的次數。

Histogram 與 Summary 都能描述分布，選擇時還要考慮跨實例聚合、精度與用戶端支援。這裡以 Classic Histogram 說明 bucket；Prometheus 另支援 Native Histogram。參考 Metric 型別與 Histograms and summaries。

Loki

把分散的事件紀錄集中保存

結帳在 10:32 失敗，處理請求的 Pod 卻不一定還在原處。集中保存 Log，才能跨實例查找當時留下的線索。

Loki 的起源與用途

Loki 是集中儲存、搜尋與分析 Logs 的系統。Grafana Labs 在 2018 年啟動專案，Tom Wilkie 與 David Kaltschmidt 的早期設計文件推動了它的誕生，同年底在 KubeCon Seattle 公開。官方以「Like Prometheus, but for logs.」描述其方向。參考 Loki 早期設計回顧與 Loki 五週年介紹。

假設 Order API 分散在 Pod A、Pod B、Pod C、Pod D、Pod E。得知「剛剛 10:32 結帳失敗」時，首先要找出是哪個 Pod 處理，以及該實例的錯誤紀錄。

Crash 後可能發生 Container Restart，也可能因 Pod 被刪除或替換而讓舊 Pod 消失；Container 重啟不等於 Pod 一定被替換。只依賴本機 Log 會受到輪替、節點與 Pod 生命週期影響，因此需要將紀錄送到集中儲存。

Log 輸出示例

在 ASP.NET Core 中，同一個 _logger.LogInformation() 呼叫若搭配帶日期的 Console 格式，可能產生 2026-09-22 08:30:01 INFO Start processing ShopId 2。ILogger 只把紀錄交給設定好的 Provider；執行到這裡不代表 Loki 已收到資料。

2. Container Runtime 將標準輸出保存為 Node Log

Container／Kubernetes 的常見配置讓程式寫入 stdout 或 stderr。Container Runtime 處理這些輸出，在 Node 上留下對應 Log，Kubernetes 可透過下列指令讀取。

讀取 Pod 的 Container Log

kubectl logs 輸出示例

資料此時仍可能只在 Node 的 Log 路徑中，尚未送入 Loki。參考 Kubernetes Logging Architecture。

3. Collector 讀取紀錄並附加分類

Collector 負責搬運 Log。例如 Grafana Alloy，或其他環境中的 Fluent Bit。舊版 Loki 教學也常見 Promtail；官方已標示 Promtail 於 2026-03-02 結束生命週期。參考 Promtail 官方狀態。

Collector 讀取的新紀錄

Metadata／Label 示例值

上述 Labels 是示例配置，不代表 Collector 自動產生所有欄位。尤其 service 的命名與映射需要在收集設定中一致。

4. Collector 透過 HTTP Push 給 Loki

傳送內容 概念示例
Timestamp 2026-09-22 08:30:01
Labels service="promotion-worker"、pod="promotion-worker-abc"、namespace="production"

這是內容概念表，不是可直接提交的 Loki API payload。Collector 依 API 格式將資料送入 Loki，Loki 才能保存並供後續查詢。

Grafana

把查詢結果變成畫面與告警

Grafana 接上資料來源，將查詢結果呈現為儀表板與探索畫面，也能定期評估告警條件。資料儲存、查詢運算與畫面呈現各有負責的元件。

三種主要使用方式

功能 操作方式 用途
Dashboard 由 Panel 對資料來源執行查詢 持續查看 CPU、Memory 與服務指標
Explore 選擇資料來源，互動式執行 PromQL 或 LogQL 逐步調查數值變化與錯誤紀錄
Alerting 定期查詢並評估規則 依告警與通知設定送出訊息

整體架構仍是應用系統提供 Metrics 與 Logs：Prometheus 負責指標收集與儲存，Alloy／Fluent Bit 等 Collector 將 Log 送入 Loki，Grafana 再查詢這些資料來源。

假設規則要觀察過去 5 分鐘的 Dify Error 數量，門檻為大於 5。Grafana 定期查詢 Loki，某次取得 8，因此滿足門檻。實際查詢需要依 Dify 的 Labels 與 Log 格式建立計數條件；純 Log 清單查詢還不是告警所需的數值結果。

告警評估：超過門檻後才進入狀態判定

flowchart TB
Evaluate["Grafana 定期評估"] -->|查詢最近 5 分鐘| Query["Loki 回傳 Dify Error 數量"]
Query --> Threshold{"錯誤數量大於 5？"}
Threshold -->|否| Next["本次未達門檻，等待下次評估"]
Threshold -->|是，範例值為 8| State["依 Pending 等設定判定告警狀態"]
State --> Ready{"已達 Alerting？"}
Ready -->|否| Wait["繼續評估條件是否持續成立"]
Ready -->|是| Policy["依通知策略與時機處理"]
Policy -->|符合通知條件| Notify["Slack / Email / 其他管道"]

由上往下讀，菱形表示判斷，箭頭直接標示條件。圖中以原先非告警、查詢成功且有資料的規則為例，沒有展開既有告警恢復、No Data 或查詢錯誤的處理。

超過門檻不等於立即通知。評估週期決定多久檢查一次；Pending period 決定條件需持續多久才進入 Alerting；通知策略還可能涉及分組、等待與靜音等設定。Pending 設為 0 時可略過等待。

以上為 Grafana-managed alert rule 的概念流程。參考 Grafana 告警評估說明。Grafana 的核心用途，是將不同監控資料來源接到同一個平台，提供查詢、視覺化、Dashboard 與 Alert。
