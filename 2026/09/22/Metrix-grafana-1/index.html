監控基礎架構

Created2026-09-22|Updated2026-09-22|Metric
|Post Views:

metric：單數，一個指標，例如「CPU 使用率這個 metric」 metrics：複數，多個指標，也常泛指「監控指標資料」

它是用來量化某個系統狀態或行為的數值指標

例如 Pod 的 Memory：

container_memory_working_set_bytes = 1,572,864,000

已經可以直接當 Metric。你可以把它理解成比較接近 raw measurement

時間 memory 08:00 1.2 GB 08:01 1.3 GB 08:02 1.5 GB

但也可以進一步加工。例如原始 Metric 是：

http_requests_total

08:00 → 10000 08:01 → 10600 08:02 → 11500

這是一個持續累加的 Counter。

你真正關心的可能是：

「現在每秒有多少 Request？」

Prometheus 就可以計算：

rate(http_requests_total[5m])

得到：

08:00 → 8 req/s 08:01 → 10 req/s 08:02 → 13 req/s

這就是由 Metric 計算出的衍生指標。

所以可以把資料流想成：

真實世界 / 系統 ↓ 原始 measurement ↓ Metric ↓ 計算 / 聚合 ↓ 衍生 Metric / 查詢結果 ↓ Grafana

例如：

Container 實際用了多少記憶體 ↓ container_memory_working_set_bytes ↓ 1,800,000,000 bytes ↓ ÷ 1024³ ↓ 1.68 GiB

甚至：

Memory Used = 1.68 GiB Memory Limit = 2 GiB

    ↓ 計算

Memory Usage = 84%

1.68 GiB 本身可以是 Metric，84% 這種加工後的結果也可以作為指標來看。

Prometheus 主要負責「定期取得 Metric → 儲存 → 查詢/計算」。實際量測通常由應用程式、OS、Kubernetes 元件或 Exporter 完成。

Pod / Container │ │ 實際使用記憶體 ▼ Linux Kernel / cgroup │ │ 提供原始資訊 ▼ 監控元件 │ │ 暴露成 Metric │ │ container_memory_working_set_bytes 1.8GB ▼ Prometheus │ ├── 定期抓取（scrape） ├── 儲存歷史資料 └── 查詢 / 計算 │ ▼ Grafana

Prometheus 本身通常沒有跑進你的 Pod 裡面說：

「我來檢查你現在用了多少 RAM。」

底層的 container/cgroup/Kubernetes 相關元件掌握這些資訊，再把它整理成 Prometheus 能讀的 Metric。

Prometheus 做的事情比較像：

Prometheus： 「每 15 秒我要來拿一次最新數字。」

08:00:00 → 1.20 GiB 08:00:15 → 1.25 GiB 08:00:30 → 1.31 GiB 08:00:45 → 1.42 GiB

這個定期取得資料的動作叫做：

Scrape（抓取）

Loki 是專門用來集中儲存、搜尋、分析 Logs 的系統

Loki 收的是什麼？

假設你的 C# Worker 有：

_logger.LogInformation(“Start processing ShopId {ShopId}”, shopId);

_logger.LogError( exception, “Failed to process promotion {PromotionId}”, promotionId);

程式實際產生：

08:30:01 INFO Start processing ShopId 2 08:30:02 INFO Loading promotions 08:30:05 ERROR Failed to process promotion 574730 08:30:05 ERROR System.TimeoutException…

這些 Log 最後可以被送進 Loki 保存。

然後你可以用 Loki 的查詢語言 LogQL 搜尋：

{service=“promotion-worker”} |= “ERROR”

意思大概就是：

幫我找 promotion-worker 裡包含 ERROR 的 Log。

  1. C# 程式先產生 Log

例如 ASP.NET Core：

_logger.LogInformation( “Start processing ShopId {ShopId}”, shopId);

假設：

shopId = 2

執行之後會產生類似：

2026-09-22 08:30:01 INFO Start processing ShopId 2

這時候 Loki 還沒有收到任何東西。

ILogger 只是把 Log 交給設定好的 Logging Provider。

例如在 Container / Kubernetes 的常見情況，程式把 Log 寫到：

stdout

也就是標準輸出。

所以你執行：

kubectl logs promotion-worker-abc

可以看到：

INFO Start processing ShopId 2 INFO Loading promotions ERROR DynamoDB timeout

這代表 Kubernetes / Container runtime 已經能取得這些 stdout/stderr Log。

  1. Kubernetes Node 上會有這些 Container Logs

概念上可以想成：

Pod │ └── Container │ │ stdout ▼ Container Runtime │ ▼ Node 上的 container log

例如 Node 上可能存在對應的 container log 檔案。

所以到這一步：

Application ↓ stdout ↓ Container Runtime ↓ Node 上的 Log

依然還沒進 Loki。

  1. Log Collector 負責「搬運」

這時候會有另一個程式專門收集這些 Logs。

例如現在 Grafana 生態常見的 Grafana Alloy，其他環境也可能使用 Fluent Bit；較舊的 Loki 架構教學則常看到 Promtail。

它做的事情可以簡化成：

「Node 有新的 Log！」

    ↓

讀取

2026-09-22 08:30 INFO Start Job 2026-09-22 08:31 ERROR Timeout

    ↓

加上一些 metadata / labels

namespace=“production” pod=“promotion-worker-abc” container=“worker” service=“promotion-worker”

    ↓

送給 Loki

所以 Log Collector 很像一個搬運工。

  1. Collector 透過網路把 Log Push 給 Loki

這一步才真的「進 Loki」。

概念上：

Log Collector │ │ HTTP │ Push Logs ▼ Loki API

送過去的內容概念上可能包含：

timestamp: 2026-09-22 08:30:01

labels: service=“promotion-worker” pod=“promotion-worker-abc” namespace=“production”

log: “INFO Start processing ShopId 2”

Loki 收到後才負責保存與後續查詢。

  1. Grafana 再去查 Loki

當你在 Grafana 寫：

{service=“promotion-worker”} |= “ERROR”

資料方向是：

你 │ ▼ Grafana │ │ LogQL Query ▼ Loki │ │ Query Result ▼ Grafana │ ▼ 你看到 Logs

所以 Grafana 通常也不是 Log 的儲存位置。

它會去查詢像 Prometheus、Loki 這些資料來源，再把結果呈現出來

例如你想看 Pod Memory

Prometheus 裡已經有：

08:00 → 1.2 GB 08:01 → 1.4 GB 08:02 → 1.7 GB 08:03 → 1.9 GB

你可以在 Grafana 建立一個 Panel，讓 Grafana 對 Prometheus 執行 PromQL：

container_memory_working_set_bytes{ pod=“promotion-worker” }

Grafana 拿到結果之後畫成：

Memory 2.0GB │ ╭─ │ ╭──╯ 1.5GB │ ╭──────╯ │ ╭────╯ 1.0GB │────╯ └───────────────────── 08:00 08:01 08:02

所以這張漂亮的圖是 Grafana 畫的，底下的資料是 Prometheus 提供的。

同樣地，你想看 Error Log。

你在 Grafana Explore 寫：

{service=“promotion-worker”} |= “ERROR”

這次 Grafana 知道你選的 Data Source 是 Loki，因此：

Grafana │ │ LogQL ▼ Loki │ │ 查詢結果 ▼ Grafana

08:31 ERROR DynamoDB timeout 08:35 ERROR OutOfMemoryException

所以你之前在 Grafana 裡面寫的 LogQL，本質上可以理解成：

你透過 Grafana 這個 UI，對 Loki 下查詢。

Grafana 還有一個重要功能：Alert

例如你設定：

過去 5 分鐘 Dify Error > 5

Grafana 定期執行查詢：

Grafana │ ▼ Loki │ ▼ 過去 5 分鐘 Dify Error = 8 │ ▼ 超過門檻 5 │ ▼ Alerting │ ▼ Slack / Email / …

這就是你之前研究的 Grafana Alert。

所以可以把 Grafana 的核心功能濃縮成：

Grafana = 把不同監控資料來源接進來，讓人查詢、視覺化、做 Dashboard 與 Alert 的平台。
