剛 Commit 完，才發現內容有錯

程式已經提交，但 database.yml 的設定不對，Commit Message 也寫得不夠清楚。這時不用把整段工作重做，只要先決定要「拆回來修改」，還是「直接重做最後一次 Commit」。

假設正在開發一個 ASP.NET Core API，目前已有三個 Commit：

  1. database.yml 的設定有錯。
  2. Commit Message 不夠精確。

目標是撤回 C，修好內容後再提交。接下來分別看 git reset 與 git commit --amend 會怎麼處理。

git reset 可以把目前分支移到另一個 Commit。選擇的模式不同，Index 與 Working Tree 會跟著出現不同結果。

它常用來處理三種情況：

  1. 已經執行 git add，但想取消暫存。
  2. 已經執行 git commit，但想撤回 Commit 並保留程式碼。
  3. 已經執行 git commit，而且確定連程式碼變更都不要了。

沒有指定模式時，git reset 預設使用 --mixed。HEAD^ 表示目前 Commit 的上一個 Commit，所以目前分支會從 C 回到 B。

Reset 前

master 與 HEAD 指向 C，database.yml 已經放進 C。

Reset 後

master 與 HEAD 回到 B，C 的檔案變更仍留在 Working Tree。

三個位置發生什麼變化

Local Repository

目前分支從 C 回到 B。C 不再是這個分支的最新 Commit。

Index

內容回到 B 的狀態，所以 C 的變更不再是 Staged。

↔︎保留差異
Working Tree

保留 C 的檔案變更，可以接著修改，不必重新寫一次。

如果 database.yml 是 C 才新增的檔案，B 與 Index 都沒有它。Reset 後，這個檔案仍留在 Working Tree，因此會顯示為 Untracked。

D 就是修改後重新建立的新 Commit。

三種模式的差別

模式 目前分支 Index Working Tree 適合情況
–soft 移到指定 Commit 保留原本內容 保留原本內容 撤回 Commit，但讓變更維持 Staged
–mixed 移到指定 Commit 重設成指定 Commit 保留原本內容 撤回 Commit，讓變更回到 Unstaged。這是預設模式
–hard 移到指定 Commit 重設成指定 Commit 重設成指定 Commit 連檔案變更都確定不要了
–hard 會直接改寫 Working Tree

尚未保存的檔案變更可能被覆蓋或刪除。只有確定這些內容不再需要時才使用。

如果只是想修正最後一個 Commit，git commit --amend 通常更直接。它會用新的 Commit 取代目前分支最後一個 Commit，不需要先把 Commit 拆回來。

Git 歷史看起來仍然只有一次功能提交，但最後那個 Commit 已經換成新的物件。

為什麼 Hash 會改

Git 的 Commit 是不可變的。git commit --amend 並不是打開原本的 Commit 直接修改，而是照下面的順序重做一次：

1. 找到目前 Commit 的 Parent

新的 Commit 會接回相同的上一個 Commit。

2. 讀取目前的 Index

Index 裡有哪些內容，新的 Commit 就會收進哪些內容。

3. 決定 Commit Message

可以換成新訊息，也可以用 –no-edit 保留原訊息。

4. 建立新 Commit

目前分支改指向新 Commit，原本的 Commit 不再是分支頂端。

兩個指令都會改寫目前分支的歷史，但使用時機不太一樣。

比較 git reset HEAD^ git commit –amend
適合情況 想先撤回最後一次 Commit，再繼續修改或重新安排暫存內容 只想直接修正最後一次 Commit 的內容或訊息
會改變目前分支歷史 會 會
會立即建立新 Commit 不會 會
會移動分支指標 會，先移到指定 Commit 會，改指向新 Commit
原本 Commit 立即消失 不會，只是不再由目前分支指向 不會，只是不再由目前分支指向

選擇方式

想把最後一次 Commit 拆回來，再慢慢整理，使用 git reset。只想把最後一次 Commit 直接換成修正版，使用 git commit –amend。

reflog 會記錄本機分支與 HEAD 曾經指向的位置，所以原本的 Commit 通常還找得到。不過這不是永久備份，過期或清理後仍可能失去紀錄。

已經 Push 的 Commit 經過 reset 或 amend 後，本機歷史會跟遠端不同。一般的 git push 通常會拒絕這種 non-fast-forward 更新，因為遠端無法只靠往前新增 Commit 走到新的歷史。

改寫已公開的歷史會影響其他開發者

強制 Push 可能讓其他人的本機分支與遠端歷史分岔。共享分支在改寫前要先確認團隊流程，不能只看本機結果正確就直接覆蓋遠端。

如果團隊允許改寫該分支，可以使用：

--force-with-lease 會先檢查遠端分支是否仍是本機預期的版本。若遠端已經出現其他人推上去的新 Commit，Push 會被拒絕，避免直接把那些內容蓋掉。

它仍然是強制更新，不代表任何情況都安全。若 Commit 已經公開，而且不應改寫歷史，通常改用 git revert 建立一個新的反向 Commit，讓遠端歷史繼續往前走。
