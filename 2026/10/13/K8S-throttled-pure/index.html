CPU

CPU 如何執行一段程式？

一段看似簡單的 C# 加法，並不是由處理器直接閱讀原始碼。程式經過編譯與執行階段處理後，會轉換成 CPU 能執行的機器指令。理解這段過程，是後續認識 Kubernetes CPU 額度與 Throttling 的起點。

CPU（Central Processing Unit，中央處理器）是負責執行機器指令的硬體。以下列 C# 程式為例，程式的目標是將兩個整數相加：

C# 加法範例

從原始碼到 CPU 動作

這段程式經過編譯與執行階段處理後，最終會轉換成 CPU 能理解的機器指令。若暫時省略底層細節，可以把處理動作整理成四個步驟：

  1. 把數值 10 放進暫存器。
  2. 把數值 20 放進另一個暫存器。
  3. 執行加法運算。
  4. 保存運算結果。

CPU 的基本指令循環

  • 取得指令Fetch
  • 解碼指令Decode
  • 執行指令Execute

這是一個用來建立概念的簡化模型

現代 CPU 會使用 Pipeline、亂序執行等技術，讓多個指令的不同處理階段彼此重疊。因此，實際運作會比 Fetch → Decode → Execute 更複雜。

CPU Core

一顆 CPU 裡面有什麼？

一顆 CPU 晶片可以包含多個 Core。每個 Core 都具備執行機器指令的能力，因此 Core 數量會影響處理器能同時推進多少工作，但實際效果仍取決於程式能否平行執行。

CPU 晶片與 Core

以下是一顆四核心 CPU 的簡化示意。外框代表整顆 CPU 晶片，裡面的四個區塊代表四個實體 Core。

CPU 晶片4 Physical Cores

  • Core 1執行指令
  • Core 2執行指令
  • Core 3執行指令
  • Core 4執行指令

假設一個 C# 程式有四個可以同時進行計算的 Thread，作業系統就有機會把它們安排到四個不同的 Core 上執行。這不代表四個 Thread 一定會永遠固定在四個 Core，實際安排仍由作業系統的 CPU Scheduler 決定。

時脈頻率代表運作節奏

時脈頻率可以想成 Core 內部協調工作的節拍。規格中的 GHz 用來描述每秒有多少個時脈週期。

以 3.5 GHz 為例 3.5 GHz = 每秒 35 億個時脈週期

這表示 Core 運作在該頻率時，每秒會經過約 35 億個時脈週期。它不代表每秒一定完成 35 億條指令，因為不同指令需要的週期數不同，現代 CPU 也可能讓多條指令的處理階段彼此重疊。

GHz 不是把所有 Core 的數字直接相加

四核心的 3.5 GHz CPU，不應解讀成一顆 14 GHz 的 CPU。3.5 GHz 描述的是核心運作時的時脈頻率，而且實際頻率還可能受到省電模式、溫度與加速機制影響而變動。

Thread 與 Core 的關係

Core 是實際執行指令的硬體。程式中的 Thread 則是可以被作業系統排程的執行單位。作業系統會把準備執行的 Thread 安排到可用的 Logical CPU 上，再由背後的實體 Core 執行工作。

SMT 為什麼會增加 Logical CPU？

SMT 的完整名稱是 Simultaneous Multithreading。它讓一個實體 Core 同時保留多組硬體執行狀態，並向作業系統呈現多個 Logical CPU。

可以把一個 Core 想成一座有多種設備的工作台。當第一個 Thread 正在等待資料，部分設備可能暫時沒有工作。SMT 讓第二個 Thread 有機會使用這些空閒資源，使同一個 Core 的利用率更高。

Intel Hyper-Threading 是 SMT 的一種實作

假設一顆 Intel CPU 有 4 個實體 Core，而且每個 Core 透過 Hyper-Threading 提供 2 個 Logical CPU，作業系統就會看到 8 個 Logical CPU。這仍然不是 8 個完整的實體 Core，因為同一個 Core 提供的兩個 Logical CPU 會共享部分執行單元、Cache 與其他硬體資源，所以效能通常不會直接變成兩倍。

判斷 CPU 效能需要同時看多項條件

Core 數量、Logical CPU 數量與時脈頻率都只描述處理器的一部分。程式的平行能力、CPU 架構、指令種類、Cache 與記憶體存取，同樣會影響最後的執行速度。

CPU 的速度怎麼決定

CPU 的速度不只看 GHz

處理器規格經常列出 Core 數量與時脈頻率，但兩顆同樣標示 3.5 GHz 的 CPU，完成同一份工作所需的時間仍可能不同。時脈只描述運作節奏，真正的速度還取決於每個週期完成多少工作，以及取得資料時需要等待多久。

先讀懂規格上的數字

以下是一組常見的處理器規格寫法：

  • Intel CPU處理器系列
  • 8 Cores實體核心數量
  • 3.5 GHz時脈頻率

上一個 tab 已說明，GHz 是時脈頻率的單位。當 Core 運作在 3.5 GHz 時，每秒大約會經過 35 億個時脈週期。

時脈頻率 3.5 GHz = 每秒 35 億個時脈週期

這個數字代表節奏有多快，不代表每秒固定完成 35 億條指令。

一個週期不等於一條指令

不同指令需要的處理時間不同。有些指令可能跨越多個週期，現代 CPU 也能透過 Pipeline、平行執行單元與亂序執行，讓多條指令的不同階段同時推進。因此，不能把時脈週期數直接當成完成的指令數。

IPC 是 Instructions Per Cycle 的縮寫，用來描述特定工作負載下，每個時脈週期平均完成多少條指令。IPC 不是永遠固定的數字，它會隨 CPU 架構、指令組合與資料等待情況改變。

GHz 較低也可能完成更多工作

以下比較刻意忽略 Cache Miss、分支預測錯誤與其他停頓，只用「時脈頻率乘以 IPC」建立基本概念：

假想處理器 時脈頻率 平均 IPC 簡化計算結果
CPU A 3.5 GHz 2 每秒約完成 70 億條指令
CPU B 3.0 GHz 3 每秒約完成 90 億條指令

這是用來理解乘法關係的簡化例子

只有在相同工作負載、單一 Core、資料供應充足，而且沒有額外停頓時，這個比較才具有概念上的意義。真實程式不能只用 GHz × IPC 判斷完整效能。

影響 CPU 效能的主要因素

因素 白話說明 可能造成的影響
時脈頻率 Core 每秒經過多少個運作節拍。 其他條件相同時，較高的時脈通常能提供更多處理機會。
IPC 每個時脈週期平均完成多少條指令。 較高的 IPC 代表每個節拍能推進更多工作。
指令種類 加法、除法、向量運算與資料載入的複雜度不同。 不同指令可能需要不同數量的週期與執行資源。
CPU 架構 Pipeline、執行單元與亂序執行能力的設計不同。 同樣的 GHz 可能產生不同的 IPC 與實際效能。
Cache 放在 Core 附近、容量較小但速度較快的資料暫存區。 需要的資料已在 Cache 時，CPU 可以減少等待。
記憶體存取 資料不在 Cache 時，需要向主記憶體讀取。 CPU 可能因等待資料而無法持續執行後續指令。

Cache 是否命中會改變等待時間

CPU 執行指令時經常需要讀取資料。資料是否已經在 Cache 中，會形成兩條不同路徑：

CPU 需要讀取資料

Cache 裡有需要的資料嗎？

  • 是，Cache Hit 從 Cache 取得資料 等待時間較短，CPU 可以較快繼續執行。
  • 否，Cache Miss 向主記憶體讀取資料 等待時間較長，資料回來後才能繼續執行。

Kubernetes 的 1000m 不是固定運算次數

CPU 額度衡量的是可使用的 CPU 時間

Kubernetes 的 1000m 不能直接換算成「每秒可以執行幾次加法」。不同 CPU 的時脈、IPC、架構、指令種類、Cache 與記憶體等待時間都不同，因此相同的 CPU 時間不保證完成相同數量的工作。

為什麼 CPU 可以同時執行很多程式

一個 Core 為什麼能同時應付多個程式？

假設電腦只有一個 Core，而且暫時不考慮 SMT，作業系統只看到一個可排程的 Logical CPU。畫面上仍能同時開啟瀏覽器、音樂播放器、開發工具與 API，原因不是單一執行單元在同一瞬間完成四份工作，而是它在不同工作之間快速切換。

四個程式都可能需要 CPU

  • Chrome瀏覽器
  • Spotify音樂播放器
  • Visual Studio開發工具
  • .NET API後端服務

一個程式可以包含一個或多個 Thread。作業系統實際排程的是已經準備好執行的 Thread，而不是把整個程式一次交給 CPU。

CPU Scheduler 決定下一個執行者

  • 等待執行Runnable Threads
  • 選擇下一個 ThreadCPU Scheduler
  • 取得處理時間1 Logical CPU

CPU Scheduler 是作業系統的一部分。它會根據可執行狀態、優先順序與其他排程條件，決定接下來由哪個 Thread 使用處理器。這張圖只保留核心關係，實際排程不一定按照固定順序輪流。

Time Sharing 讓多個工作輪流前進

Time Sharing 稱為分時共享。每個 Thread 取得一小段處理時間，時間到、主動等待，或作業系統決定改派其他工作時，下一個 Thread 會接著執行。

時間向右 →

時間片 1Chrome Thread

時間片 2Spotify Thread

時間片 3Visual Studio Thread

時間片 4.NET API Thread

每條藍色分隔線代表一次工作切換，也就是 Context Switch。

這是用來觀察輪流執行的簡化時間軸

真實順序由作業系統決定。同一個 Thread 可能連續取得時間，也可能因等待網路、磁碟或其他事件而暫時不需要 CPU。因此，排程不一定會完整走過四個程式後才回到第一個程式。

Context Switch 保存目前進度，再換下一個 Thread

  • 暫停目前工作Pause
  • 保存並載入狀態Save / Restore
  • 繼續下一個 ThreadResume

作業系統會保存目前 Thread 的必要執行狀態，例如程式計數器與暫存器內容，再恢復下一個 Thread 先前保存的狀態。這樣才能從正確的位置繼續執行。

切換本身也需要時間

Context Switch 不是應用程式的實際工作。切換過度頻繁時，保存狀態、恢復狀態與重新取得資料都可能增加額外成本。

Concurrency 與 Parallelism 不相同

概念 白話說明 執行情況
Concurrency 並發 多個工作都在一段時間內持續推進。 單一 Logical CPU 可以透過 Time Sharing 快速輪流執行。
Parallelism 並行 多個工作在同一個瞬間真正同時執行。 需要多個可同時執行的 Core 或 Logical CPU。

單一 Logical CPU 上的多工主要是並發。切換速度夠快，加上部分 Thread 經常在等待輸入輸出，因此使用體感會像多個程式同時運作。多個 Core 或 Logical CPU 則能讓多個 Thread 在同一時間真正並行。

CPU Scheduler 與 Kubernetes Scheduler 負責不同工作

兩個 Scheduler 的排程層級不同

作業系統的 CPU Scheduler 決定哪個 Thread 取得 Logical CPU。Kubernetes Scheduler 則決定尚未排程的 Pod 應該放到哪一個 Node。兩者名稱相似，但處理的對象與範圍不同。

Kubernetes 的 1000m

Kubernetes 的 1000m 代表多少 CPU？

Kubernetes 用 CPU 單位描述容器需要或最多可以使用多少處理能力，也常用 m 表示 millicpu，也就是千分之一個 CPU。這個單位描述的是一段時間內可使用的運算能力，不是固定的指令數，也不是把某顆實體核心切成幾塊。

0.5 CPU 不是半顆實體核心

0.5 CPU 可以理解為一份「CPU 執行時間額度」。它沒有指定只能使用某一顆核心的左半邊或右半邊，也不代表容器會固定綁在某顆核心上。

額度是按時間累積，不是按核心形狀切割

假設一個 Logical CPU 在 100ms 內最多能提供 100ms 的 CPU 執行時間，平均 0.5 CPU 就相當於在同一段時間內使用 50ms 的 CPU 執行時間。

requests 與 limits 的 500m 意義不同

以下設定同時把 requests.cpu 與 limits.cpu 設為 500m：

  • requests.cpu: 500mKubernetes Scheduler 選擇 Node 時，會把這個容器計為需要 0.5 CPU。這個值用於排程計算，本身不是執行時的最高用量。
  • limits.cpu: 500m容器最多只能取得平均 0.5 CPU 的運算能力。Linux 會以 cgroup CPU 頻寬控制限制用量，超過額度時可能發生 Throttling。

假設 Linux 的 CFS bandwidth period 設為 100ms，而容器的 CPU 上限是 500m。概念上，每個週期會有 50ms 的 CPU 執行時間額度。

如果只有一個持續運算的 Thread，它可以在某個 Logical CPU 上連續執行約 50ms，接著因額度耗盡而等待下一個週期。這是為了理解額度所做的簡化示意，實際執行時間仍會受到作業系統排程與其他工作影響。

多個 Thread 會共用同一份額度

容器內有多個 Thread 時，它們消耗的是同一份 CPU 額度。如果兩個 Thread 分別在兩個 Logical CPU 上並行，每經過 1ms 的實際時間，合計可能消耗約 2ms 的 CPU 執行時間。

1000m = 每 1 秒可使用 1 秒 CPU time

硬體數量也會形成上限

容器的 limits.cpu 是 2000m，但 Node 只有一顆 Logical CPU，實際能使用多少？

查看答案

實際最多約為 1000m。2000m 允許每秒最多累積兩秒 CPU 執行時間，但一顆 Logical CPU 每秒最多只能提供一秒 CPU 執行時間。設定允許的額度高於硬體容量時，硬體仍是最後的上限。

單一 Thread 也會形成上限

假設 Node 有 4 Core，容器的設定如下，而 C# 程式只有一個 Thread 持續執行 CPU 密集型計算：

單一 Thread 情境

這個容器實際上最多會使用多少 CPU？

  1. 1000m
  2. 2000m
  3. 4000m

查看答案

答案是 A. 1000m。單一持續運算的 Thread 同一瞬間通常只能在一顆 Logical CPU 上執行。即使 Node 有四顆核心，而且容器允許使用 2000m，單一 Thread 仍只能累積約 1000m 的 CPU 使用量。

條件 數量
Node 可用 CPU 4000m
容器 CPU Limit 2000m
CPU 密集型 Thread 1
實際最大 CPU 使用量 約 1000m

實際用量受到三個條件限制

  • 硬體資源Node 有多少可用的 Logical CPU。
  • 程式平行能力有多少 Thread 或工作可以同時進行運算。
  • CPU Limit容器最多允許累積多少 CPU 執行時間。

四個 Thread 如何耗盡一個 100ms 額度？

Node 有四顆核心、容器 Limit 是 1000m，而四個 Thread 同時執行 CPU 密集型運算，Linux 可能如何處理？

  1. 只允許其中一個 Thread 執行，其他三個等待。
  2. 四個 Thread 可以同時執行，但會快速耗盡 CPU 額度，接著全部被 Throttle。
  3. 四個 Thread 持續執行，每個 Thread 的運算速度自動降低為 25%。

查看答案

答案是 B。假設 Linux 的 CPU quota period 是 100ms，1000m 代表這個週期合計有 100ms 的 CPU 執行時間。四個 Thread 若分別在四顆 Logical CPU 上並行，每個執行約 25ms 就會共同用完額度。

1000m = 100ms CPU time ÷ 100ms period

4 Threads × 25ms = 100ms CPU time

一個 100ms quota periodContainer limit: 1000m

0ms25ms100ms

經過約 25ms 後，容器已經累積使用完整的 100ms CPU 額度。接下來約 75ms，受限制的 Thread 會等待下一個週期補充額度。

CPU Limit 限制的是整個容器的累積 CPU time

Thread 數量增加不會增加 CPU 額度。多個 Thread 並行只會讓同一份額度更快被消耗完。

Throttling

CPU Throttling 發生時，程式並沒有被殺掉

當容器想使用的 CPU 超過設定上限時，Linux 會暫時限制受管制的 Thread，等下一個額度週期再繼續執行。工作仍然存在，但完成時間可能被拉長。

從一個 .NET API 情境開始

假設 .NET API 容器的 CPU request 是 500m，CPU limit 是 1000m：

.NET API CPU 資源設定

大量 API Request 同時進入，CPU 使用需求達到 3000m 時，容器會被殺掉嗎？

查看答案

不會只因 CPU 需求超過 Limit 就被殺掉。Linux 會透過 CPU throttling 暫時限制執行，讓受限制的 Thread 等待下一次可用額度。這和記憶體超過上限後可能發生的 OOMKilled 不同。

CPU Throttling = 工作仍在，等待 CPU 額度

額度耗盡後會反覆等待與繼續

  • 執行工作消耗 CPU quota
  • 額度耗盡Quota exhausted
  • 暫停排程Throttled
  • 下個週期繼續Quota refilled

程式需要 3000m 的運算能力時，Linux 會先允許容器執行並消耗額度。該週期的額度用完後，受限制的 Thread 暫時停止排程；下一個週期補充額度後再繼續，如此反覆直到工作完成。

CPU time 不等於 Response Time

假設一個 API 的計算總共需要 100ms CPU time。如果 CPU Limit 讓這些計算必須跨越多個週期，實際經過的 Response Time 可能變成 200ms、300ms，甚至更久。

  • 執行一部分消耗 CPU time
  • 等待額度Throttled
  • 繼續執行消耗 CPU time
  • 再次等待Throttled
  • 工作完成Response returned

CPU 工作量相同，牆上時鐘經過的時間可能更長

CPU time 計算實際在 CPU 上執行的時間；Response Time 還包含等待 CPU 額度、排程、輸入輸出與其他延遲。Throttling 增加的是等待時間，因此 API 延遲可能上升。

Grafana 上可能同時出現的現象

  • Pod 仍在執行沒有因 CPU Limit 而出現 OOMKilled。
  • CPU Usage 接近 Limit容器持續想使用可取得的 CPU 額度。
  • API Response Time 上升部分計算時間被拆到後續週期。
  • 嚴重時出現 Timeout程式仍存活，但回應沒有在期限內完成。

requests 不會直接觸發 Throttling

  • requests.cpu: 500m主要供 Kubernetes Scheduler 排程時計算資源需求。使用量超過 500m，不代表立刻發生 Throttling。
  • limits.cpu: 1000m這是 Linux 執行時限制 CPU 用量的上限。容器耗盡該週期額度後，才會因 CPU quota 被 Throttle。

排查 EKS API 效能時可觀察的 Metrics

Metric 代表意義 判讀方向
container_cpu_cfs_throttled_periods_total 累積發生 Throttling 的 CPU enforcement period 數量。 持續增加表示容器反覆在週期內耗盡 CPU 額度。
container_cpu_cfs_throttled_seconds_total 容器累積被 Throttle 的時間。 搭配變化速率觀察等待 CPU 額度的時間是否持續增加。

在 EKS 排查 API 效能時，可把這兩項 Metrics 與 CPU Usage、CPU Limit、Response Time 和 Timeout 放在同一段時間範圍內比較。單看 CPU Usage 接近上限，無法判斷延遲是否確實由 Throttling 造成。
