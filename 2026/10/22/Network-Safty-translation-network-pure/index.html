Translation API 網路與授權排查

Created2026-10-22|Updated2026-10-23|network-safety
|Post Views:

案件

Translation API 的 503，該從哪一層開始查？

辦公室裡使用 Claude Desktop 呼叫公司 Translation API 時，畫面回傳 HTTP 503。這個狀態只能證明某一層 HTTP 服務回了錯誤，還不能直接判定是 VPN、DNS、憑證、Port 或 Pod 故障。

排查的關鍵是先找出真正送出 HTTP 請求的工具，再沿著 DNS、TLS、入口代理、Kubernetes 與 API 授權逐層確認。每一層都回答不同問題，不能只靠一行錯誤訊息跳到根因。

整體排查地圖

本文的證據邊界

現有資料可以說明程式邏輯、兩種網路環境的 DNS 結果與兩套部署設定，但缺少事故當下的完整回應標頭、代理日誌及實際 Kubernetes 狀態。因此，文章會區分已確認事實、排查假設與仍待現場確認的項目。

InternalIpAuthorizationMiddleware

內部請求要同時符合兩個條件

Translation API 接到請求時，會先檢查來源 IP 是否在白名單中，以及 Authorization 標頭是否帶有正確的內部固定 Token。兩個條件都符合時，程式才會為這次請求建立內部使用者身分。

任一條件不符，請求仍會繼續往後處理。這段 Middleware 本身不會封鎖外部 IP，也不會在 IP 檢查完成後直接跳進 API Action。

%%{init: {"flowchart": {"nodeSpacing": 20, "rankSpacing": 25}, "themeVariables": {"fontSize": "14px"}}}%%
flowchart TB
Request["請求進入 Translation API"] --> Ip{"來源 IP 在白名單嗎？"}
Ip -->|否| Continue["不建立內部身分"]
Ip -->|是| Token{"Authorization 是正確的內部固定 Token 嗎？"}
Token -->|否| Continue
Token -->|是| Identity["建立 InternalUser 身分與 Admin claim"]
Identity --> Authentication["執行 UseAuthentication"]
Continue --> Authentication
Authentication --> Authorization["路由階段執行 UseAuthorization"]
Authorization --> Endpoint["依 endpoint 與業務規則決定結果"]

兩條失敗分支會匯入一般後續流程，不代表請求已獲准，也不代表請求立刻被拒絕。

Middleware 的執行順序

Startup.Configure 先執行 InternalIpAuthorizationMiddleware，接著執行 UseAuthentication()，最後在路由階段執行 UseAuthorization()。內部請求即使取得內部身分，仍會通過後面的驗證與授權流程。

Firebase 是 Google 提供的應用服務。這個專案使用 Firebase 的登入驗證功能，一般使用者登入後取得 Firebase Token，再由 API 的 JWT 驗證設定檢查簽發者、使用對象與有效期限。API 是否要求登入，仍取決於該 endpoint 的授權設定。

來源 IP 如何取得

程式先讀取網路連線的 RemoteIpAddress。如果請求帶有 X-Forwarded-For 標頭，就改用標頭中的第一個 IP。這項處理是為了支援代理或負載平衡器，因為網路連線的直接對方可能是代理，而不是原始呼叫者。

白名單來自 InternalAuth:AllowedIps。目前 appsettings.json 與 appsettings.Development.json 都列出三個 IP，部署環境仍可能覆寫這些設定。

信任邊界

這段程式沒有自行驗證 X-Forwarded-For 是否由可信任代理寫入。入口代理如何清理、保留或追加這個標頭，會直接影響 IP 判斷能否信任。

內部固定 Token 與 Firebase Token

憑證 來源 驗證方式 用途
內部固定 Token InternalAuth:PermanentToken Middleware 完整比對 Authorization: Bearer <Token> 與來源 IP 符合條件時建立內部身分
Firebase Token 一般使用者登入流程 JWT 驗證簽發者、使用對象與有效期限 確認一般使用者身分

內部固定 Token 不會在每次請求時產生。appsettings.Development.json 有自己的設定值，其他環境使用哪個值，須以實際載入的設定為準。固定 Token 必須保密，公開文件不應列出實際內容。

建立的身分與 Admin claim

兩個條件都符合時，Middleware 會建立已驗證的 ClaimsIdentity，放入名稱 InternalUser、代表內部使用者的 Email，以及值為 Admin 的角色 claim。Claim 是附在使用者身分上的資料，後續授權程式可以讀取。

Admin claim 不等於所有管理員權限

UserRepo 會另外從 Email 與角色名單計算業務角色。請求最後能執行哪些功能，仍要看 endpoint 與業務邏輯如何檢查身分及角色。

程式位置對照

位置 對應行為
Startup.cs 註冊內部 IP Middleware、Firebase JWT 驗證與授權流程
Utils/InternalIpAuthorizationMiddleware.cs 取得 IP、比對白名單與固定 Token、建立內部身分
Repos/UserRepo.cs 從身分中的 Email 計算業務角色
appsettings.json、appsettings.Development.json 提供白名單與內部固定 Token 的預設設定

[Authorize]

[Authorize] 檢查的是已驗證身分

[Authorize] 是 ASP.NET Core 放在 Controller 或 Action 上的授權標記。請求進入標有 [Authorize] 的 Action 前，框架會要求目前請求具有已驗證的使用者身分。

這個身分可能來自 Firebase JWT，也可能由前一段的內部 IP Middleware 建立。單獨使用 [Authorize] 只要求已有驗證身分，沒有指定必須是 Admin 或 Translator。

flowchart TB
Request["請求進入 API"] --> Mark{"目標 Action 標有 [Authorize] 嗎？"}
Mark -->|否| Action["進入 Action"]
Mark -->|是| Identity{"目前有已驗證的身分嗎？"}
Identity -->|否| Reject["框架拒絕進入 Action"]

Action --> Role{"Action 或 Service 另有角色檢查嗎？"}
Role -->|否| Logic["執行後續程式邏輯"]
Role -->|是| Business{"業務角色符合要求嗎？"}
Business -->|否| Deny["業務授權拒絕操作"]
Business -->|是| Logic

沒有標示 [Authorize]，只代表進入 Action 前沒有強制要求驗證身分，不保證 Action 一定成功。

Action 內可能另有角色檢查，也可能因資料、外部服務或部署入口限制而失敗。網路可達、身分驗證與業務授權是三個不同層次。

Token、Email 與業務角色的鏈路

%%{init: {"flowchart": {"nodeSpacing": 20, "rankSpacing": 25}, "themeVariables": {"fontSize": "14px"}}}%%
flowchart TB
Firebase["Firebase Token"] --> Auth["UseAuthentication 驗證 Token"]
Internal["白名單 IP 加內部固定 Token"] --> Middleware["InternalIpAuthorizationMiddleware 建立身分"]
Auth --> Email["身分中的 Email claim"]
Middleware --> Email
Email --> Repo["UserRepo.getRoles"]
Repo --> User["先加入 User"]
Repo --> Lists["比對 Admin 與 Translator 名單"]
Lists --> Roles["產生 RoleType"]

兩種 Token 負責建立或驗證身分，UserRepo 再用 Email 計算自己的業務角色。

  1. UserRepo 從目前身分的 Email claim 取得 CurrentUserId。
  2. getRoles() 先加入基本的 User 角色。
  3. 如果有 Email，就用它對照 _N1CONFIG:Roles:Admin 與 _N1CONFIG:Roles:Translator，加入符合的 RoleType。
  4. GET /api/translations/roles 的 AdminController.GetRoles() 只把 UserRepo.Roles 轉成文字回傳，不負責驗證 Token，也不會賦予角色。

GET /api/translations/roles 本身沒有標示 [Authorize]。若請求沒有 Email claim，依目前算法會回傳 User。

例如 RollbackTranslation 同時標有 [Authorize]，並在 Action 內呼叫 CheckAuthRole(RoleType.Admin)。只取得已驗證身分，仍不足以執行這項操作。

現行程式與舊草稿的差異

目前的 UserRepo.getRoles() 已使用 CurrentUserId 判斷角色。舊草稿所述「固定檢查某個寫死的 Email」不符合現行程式碼，不能列為現行 Bug。程式目前使用字串的 Contains 比對角色名單；若要評估嚴謹度，仍需檢查設定格式與實際資料。

HTTP 503

503 錯誤描述的是代理與上游的連線結果

處理請求的代理在連向上游服務時，或在收到上游回應標頭之前，遇到連線失敗或中斷，最後回傳 HTTP 503。這段訊息不能證明 Translation API 已經收到請求，也不能直接證明某個 Port 設錯。

Envoy 會產生類似格式，但只靠錯誤文字還不能確認現場一定是 Envoy。回應來自哪一層代理，仍須查看完整 HTTP 回應標頭與該層的存取日誌。

Claude 的工具可能在本機或雲端執行

%%{init: {"flowchart": {"nodeSpacing": 20, "rankSpacing": 25}, "themeVariables": {"fontSize": "14px"}}}%%
flowchart TB
Claude["Claude Desktop 發起工具呼叫"] --> Type{"Translation 請求由哪種工具送出？"}
Type -->|本機 MCP 或桌面擴充| Local["使用電腦送出 HTTP 請求"]

Claude 會使用雲端服務處理對話，但真正發送 Translation HTTP 請求的位置，取決於實際使用的工具。

本機 MCP 使用執行它的電腦當時的網路、DNS 與代理設定。遠端 Connector 從雲端發出請求，電腦連上公司內網或 VPN，不會讓雲端工具自動取得相同的內網路由。Chrome Extension 的執行位置也要依當時使用的功能確認，不能只看擴充功能名稱。

兩種 Connector 的執行位置可參考 Claude 的本機與遠端 Connector 說明。

當時一般 Wi-Fi 對該網域解析到公開 IP 35.201.120.17。即使請求從雲端送出，也不能只憑「公司內網位址無法從雲端連接」這項推測，就斷定該次請求連到私有 IP 或已找出 503 根因。

四項推測都需要額外證據

排查假設 目前能確認的事 下一步證據
VPN 或路由 一般本機子程序使用同一台電腦的路由，不能直接認定 MCP 沒有繼承路由，也不宜先套用 HTTP_PROXY 或 HTTPS_PROXY。 比較終端機與工具的 DNS、環境變數、代理設定及執行位置。雲端工具則檢查雲端可到達的入口。
mTLS 或 SSL 憑證 remote connection failure 沒有指出是否在 TLS 握手失敗，也無法證明是私有 CA。 查看實際端點、TLS 錯誤與代理日誌。不要把 NODE_TLS_REJECT_UNAUTHORIZED=0 當成解法，CA 問題應正確設定信任鏈。
DNS 解析 公司內網與一般 Wi-Fi 的 DNS 答案不同，但不知道事故請求的工具解析到哪個位址。 在工具實際執行環境查 DNS；固定測試某個 IP 時用 curl --resolve 保留原網域的 HTTPS 條件。
防火牆或 IP 白名單 基礎設施限制可能存在，但缺少防火牆或入口日誌。Origin 與 CORS 不代表網路可達，內部 IP Middleware 也沒有封鎖所有外部 IP。 檢查入口、防火牆與負載平衡器日誌，並核對實際網路政策。

排查假設不是事故結論

要還原當時鏈路，至少需要確認使用的是本機 MCP、遠端 Connector 或哪項 Chrome Extension 功能，並保留請求時間、完整回應標頭及對應代理日誌。

503 可能發生在 Kubernetes 上游路徑

flowchart TB
Client["呼叫方"] -->|HTTPS| Proxy["入口代理"]
Proxy -->|轉送上游| Service["Kubernetes Service"]

此圖只表示需要逐層核對的上游路徑，不代表每一層都已證實存在或已確認故障。

看到 503 時，先確認請求抵達哪一層，再檢查該層連往下一層的設定與狀態。程式庫中存在兩套部署資料，不能把兩套 Port 直接放在一起判定衝突。

部署資料 程式庫中的設定 尚需確認
Helm 部署 charts/translation-web-api/values-tw-qa.yaml 與 values-tw-prod.yaml 的 api.servicePort 都是 50350。根目錄 Dockerfile 以建置參數 NYS_PORT 設定 EXPOSE，並用 --urls http://*:${NYS_PORT} 啟動。pipeline/build-config.sh 匯出的 Port 是 50350。 共用 pipeline 如何傳入 NYS_PORT、Helm 模板產出的 Service targetPort，以及實際 Pod 監聽 Port。
k8s/template 部署 deploy.yaml 的 containerPort 與 probe Port 是 80；svc.yaml 的 Service Port 與 targetPort 也都是 80。 這套模板是否仍用於發生錯誤的環境。

現有程式庫沒有足夠證據將 Port 不一致列為根因。判斷時應以出錯環境實際部署出的 Deployment、Service 與 EndpointSlice 為準。

Readiness 與記憶體只能提供排查方向

k8s/template/deploy.yaml 的 readiness probe 呼叫 /api/translations/health?readness。這個路徑對應的 AdminController.Health() 直接回傳 OK，沒有檢查 MongoDB 或 Firebase。

如果 probe 失敗，應先查看 Pod 是否啟動、實際監聽 Port、probe 的連線結果及 Pod 事件，不能直接歸因於資料庫或 Firebase 設定。

Helm values 設定的記憶體上限為 1000Mi，另有 COMPlus_GCHeapHardLimit。Pod OOM 或反覆重啟也是排查方向，但只有 Pod 狀態、事件或前一次容器日誌出現對應證據時，才能列為原因。

Envoy 在這條鏈路中扮演什麼角色

Envoy 是代理伺服器軟體，可以放在呼叫方與 Translation API 之間，負責接收請求、選擇上游服務、轉送流量、處理重試並記錄連線狀態。Envoy 也常被用在 Istio 中；Envoy 是代理軟體，Istio 是管理服務間流量的系統。

套用到這個案例，可理解為「呼叫方 → 代理，可能是 Envoy → Translation API」。503 訊息表示代理嘗試連接後方服務，但在收到回應標頭前連線失敗或中斷。因此，錯誤可能由代理回給呼叫方，Translation API 不一定收到請求。

要確認是否為 Envoy，以及它位於哪一段連線，需要對照 HTTP 回應標頭和代理日誌。可參考 Envoy 存取日誌文件中的 response flags 與 response code details，區分上游連線失敗、連線被重設及其他 503 情境。

TLS 錯誤

TLS 握手完成前，連線就中斷

這是呼叫端與某個 HTTPS 端點建立安全連線時，在 TLS 握手完成前就中斷所回報的錯誤。以 Node.js 的用語來說，secureConnect 會在握手成功後才發生，這次連線沒有走到該事件，也沒有取得 HTTP 回應，因此沒有 HTTP 狀態碼。

單靠這行訊息，無法判定是哪個端點關閉連線，也不能確認是憑證、網路或代理設定造成。

TLS 錯誤與 HTTP 503 發生在不同階段

前半段是呼叫端到 HTTPS 入口，後半段是入口到 Translation 上游。兩段連線可能各自失敗。

比較 HTTP 503 upstream error TLS socket error
呼叫端收到什麼 一個 HTTP 503 回應 連線錯誤，沒有 HTTP 回應
已能確定的階段 呼叫端已收到某個 HTTP 服務或代理的回應，失敗可能發生在它往上游的連線。 呼叫端與其連接的 HTTPS 端點尚未完成 TLS 握手。
不能直接推論 一定是特定代理、Pod 或 Port 的問題。 一定是憑證、防火牆或 Translation API 的問題。

如果 Claude 使用的工具在連上 HTTPS 入口前就中斷，呼叫端會看到 TLS 錯誤。如果工具已連上入口，而入口往 Translation 上游的連線失敗，呼叫端才可能收到代理回傳的 503。兩種訊息可能出現在不同次請求，同一次呼叫的不同網路區段也可能各自有不同失敗原因。

同一網域在兩種網路下解析到不同入口

這裡的「內網」指電腦連公司內網時的查詢，「外網」指電腦連一般 Wi-Fi 時的查詢。以下紀錄描述兩個測試環境，不是同一個環境先後取得不同答案。

這是分流 DNS 的觀察結果。它只能證明查詢結果不同，不能單靠 DNS 推定兩個入口後方的完整轉送路徑。

測試網路 當時的解析結果
公司內網 translation.qa.91dev.tw → private-ingress-alb.eks.91dev.tw → internal-private-eks-ingress-alb-1654285349.ap-northeast-1.elb.amazonaws.com → 10.50.45.132 或 10.50.40.7
一般 Wi-Fi translation.qa.91dev.tw → 35.201.120.17

公司內網的結果是私有 IP，一般 Wi-Fi 的結果是公開 IP。這能確認當時兩個網路環境走向不同入口，但不能證明入口後方如何轉送，也不能單憑公開 IP 判定由哪個負載平衡器回應。

要分析 Claude 的呼叫，仍須先確定替 Claude 發送 HTTP 請求的工具在哪裡執行，以及它當時解析到哪個位址。

直接使用公開 IP 測試改變了 HTTPS 條件

這次測試使用 IP 當作 HTTPS 網址的主機名稱，與呼叫 https://translation.qa.91dev.tw 的條件不同。TLS 的 SNI、憑證名稱驗證與 HTTP Host 都會受到網址主機名稱影響。

這不代表請求「沒有 Host header」。如果 HTTP 請求成功送出，Host 會是該 IP。上述 curl: (35) 只說明 TLS 連線失敗，無法直接推定為憑證名稱不符，也沒有取得 HTTP 503。

指定 IP，同時保留原網域條件

%%{init: {"flowchart": {"nodeSpacing": 20, "rankSpacing": 25}, "themeVariables": {"fontSize": "14px"}}}%%
flowchart TB
Curl["curl --resolve"] --> Dns["只覆寫本次 DNS 結果為 35.201.120.17"]
Dns --> Tls["URL 與 TLS SNI 保留 translation.qa.91dev.tw"]
Tls --> Http["HTTP Host 保留 translation.qa.91dev.tw"]
Http --> Result["觀察指定入口的 TLS 與 HTTP 結果"]

--resolve 只控制本次連線目的 IP，不會讓一般 Wi-Fi 取得公司內網的存取能力。

比較公司內網、一般 Wi-Fi 與 Claude 工具的結果時，應記錄每次執行位置、DNS 答案、完整回應或錯誤，以及發生時間。

參考資料：curl 的名稱解析說明、curl 錯誤碼。

外網存取方式

先取得有效的 Firebase Token，再呼叫 API

目前紀錄的操作方式是先透過 VPN 開啟 QA 網站並完成登入，再從瀏覽器的 Network 面板取得 Firebase Token，最後把 Token 放入 API 請求的 Authorization 標頭。

%%{init: {"flowchart": {"nodeSpacing": 20, "rankSpacing": 25}, "themeVariables": {"fontSize": "14px"}}}%%
flowchart TB
Vpn["連上可存取 QA 的公司網路或 VPN"] --> Site["開啟 translation.qa.91dev.tw 並登入"]
Site --> DevTools["在瀏覽器 Network 面板選擇任一 API request"]
DevTools --> Token["讀取 Authorization: Bearer eyJ..."]
Token --> Call["帶 Firebase Token 呼叫 Translation API"]
Call --> Valid{"Token 仍在有效期內嗎？"}
Valid -->|是| Auth["API 驗證 Token 與 endpoint 授權"]
Valid -->|否| Expired["回傳 401，重新登入取得 Token"]

這條流程描述 Firebase Token 的取得與使用，不等同於內部固定 Token 的驗證路徑。

操作步驟

  1. 開啟 translation.qa.91dev.tw。QA 需要公司內網或 VPN。
  2. 完成登入後開啟瀏覽器開發者工具。
  3. 在 Network 面板選擇任一 API request。
  4. 從 request headers 找到 Authorization: Bearer eyJ...。
  5. 將 Token 放入 API 呼叫的 Authorization 標頭。
項目 說明
Firebase Token 有效期 1 小時，過期會回傳 401。
QA 環境 只能從內網存取，需要 VPN。
Production 環境 translation.91app.io 或 translation.io.91app.com。

Token 屬於敏感憑證

文章與截圖不應保留完整 Token。分享排查紀錄時只保留足以辨識憑證類型的開頭，並遮蔽其餘內容。

環境資訊

QA 與 Production 使用不同入口

現有資料指出 QA 使用內網 ALB，需要公司網路或 VPN；兩個 Production 網域則使用 GCP CLB。這張圖只呈現已知的入口差異，不推定入口後方的完整服務拓撲。

排查時先固定環境

記錄網域、網路位置、DNS 結果與發生時間，再比對該環境的入口日誌與 Kubernetes 狀態。不同環境的 Port 或模板不能直接混在一起判定衝突。
