把 Develop 的最新進度同步到 Feature

登入功能尚未完成時，遠端 develop 可能已經加入其他人的修改。這篇文章從 HEAD、Branch 與 Commit 的關係開始，逐步說明如何在不遺失目前工作的前提下，把最新開發基礎整合進 feature/login。

情境中的三個 Branch

master

正式環境使用的分支，保存準備發布或已發布的版本。

develop

團隊日常開發與整合功能的分支，其他同事會持續把新程式碼合併進來。

feature/login

從 develop 建立，用來開發登入功能。部分功能已完成並建立 Commit，但整體工作尚未結束。

兩天後，兩條開發歷史已經分開前進

建立 feature/login 時，兩個 Branch 都停在 Commit B。之後遠端 develop 前進到 D，Feature 也累積了 F1 與 F2。

中央問題

停在 feature/login 時，可以直接整合遠端 develop 嗎？
可以直接整合

git pull –no-rebase origin develop 會先取得遠端更新，再把 origin/develop 合併進目前所在的 feature/login。

也可以分開執行

先執行 git fetch origin，再明確選擇 git merge origin/develop 或 git rebase origin/develop，流程較容易檢查。

不必先更新本機 develop

只要目標是把遠端 develop 的最新內容整合進 Feature，就不必先切回本機 develop。先更新本機 develop 再切回 Feature 也能完成，但多了一次切換，結果取決於最後合併或 Rebase 的來源是否正確。

工作目錄先保持乾淨

提交已完成內容，或用 git stash 暫存尚未完成的修改。

→
取得遠端更新

執行 git fetch origin，更新 origin/develop。

→
選擇整合方式

共用 Feature 優先考慮 Merge；個人 Feature 可以評估 Rebase。

HEAD 記錄目前工作位置

書籤比喻

專案裡可以同時有 master、develop 與 feature/login。HEAD 像一張書籤，標示目前選擇哪一條 Branch 進行查看、修改與提交。

切換前

HEAD → develop → Commit C

git switch
feature/login

切換後

HEAD → feature/login → Commit D

HEAD

目前檢出位置的特殊 Reference。

→
Branch Reference

容易記住的名稱，例如 develop，指向一個 Commit。

→
Commit

保存專案快照、父 Commit 與提交資訊。

Reference 讓 Commit 容易被找到

develop 是會移動的 Reference

Commit Hash 可能是 a83f92c…。Branch 名稱提供穩定、容易閱讀的入口，新的 Commit 建立後，該名稱可以移向新的 Commit。

切換 Branch 時，工作目錄也會跟著調整

develop 的版本

LoginService.cs 有 100 行。切換到這個 Branch 時，Git 準備對應版本供查看與修改。

feature/login 的版本

LoginService.cs 有 150 行。Git 會依版本差異更新 Working Tree；若存在未提交修改，Git 會先判斷能否安全保留。

Checkout 的概念

檢出表示把選定版本準備到工作目錄。git switch 專注於切換 Branch；較早期的 git checkout 同時也能操作檔案。

建立 Commit 時，HEAD 決定哪個 Branch 前進

提交前

  • HEAD → feature/login
  • feature/login → D
  • develop → C
git commit -m
“Complete login API”

提交後

  • 建立 Commit E
  • feature/login → E
  • develop 仍指向 C
HEAD 也能直接指向 Commit

這種狀態稱為 Detached HEAD，適合暫時查看歷史版本。一般開發時，HEAD 會指向 Branch，讓新 Commit 自動推進正確的 Branch Reference。

HEAD 在 Repository 裡的實際位置

.git/HEAD

內容可能是 ref: refs/heads/develop。

→
refs/heads/develop

保存或解析出目前 Commit Hash。

→
a1b2c3…

Git 依 Hash 找到對應的 Commit 物件。

查看 HEAD 
cat .git/HEAD
ref: refs/heads/develop
Reference 不一定只存在於鬆散檔案

一般非 Bare Repository 常能在 .git/refs/heads/ 找到 Branch Reference。Git 也可能把 Reference 儲存在 packed-refs 等結構中，因此概念重點是名稱與 Commit 的指向關係，不是固定檔案排列。

Commit 保存快照，也記錄歷史關係

develop 已累積三個 Commit

每個 Commit 保存當時的專案快照，也記錄父 Commit 等資訊。Commit C 的 Parent 是 B，B 的 Parent 是 A。

從 develop 建立 Feature

建立並切換 Branch 
git switch develop
git switch -c feature/login
1. 切換到 develop

HEAD 指向 develop，目前基礎版本是 Commit C。

2. 建立 feature/login

Git 建立新的 Branch Reference，讓它同樣指向 Commit C。

3. 切換 HEAD

HEAD 改為指向 feature/login，但不會因此複製歷史或建立新 Commit。

建立 Branch 的當下，兩個名稱仍指向同一個 Commit

Feature 的第一個 Commit 才讓歷史分岔

開發登入功能 
git add .
git commit -m "Add login API"

Commit D 建立後

develop 保持在 C，feature/login 移到 D，D 的 Parent 是 C，HEAD 仍指向 feature/login。

Commit、Branch、HEAD 與 Merge 各自解決什麼問題

概念 主要作用 實際解決的問題
Commit 保存專案快照與父 Commit 如何保留並串起歷史版本
Branch 用可移動的 Reference 標記進度 如何讓不同開發方向各自前進
HEAD 標記目前檢出位置 如何知道新 Commit 要接在哪個方向
Merge 整合不同歷史 如何把分開發展的成果重新接在一起
如果沒有 HEAD

Git 仍可透過 Commit 與 Branch 形成分岔歷史，但每次提交都需要另一種方式指定要更新哪個 Branch。git commit –branch feature/login 是用來說明概念的假想指令，實際 Git 沒有這個選項。HEAD 讓目前位置成為後續操作的共同起點。

開 Branch 是新增一個可以獨立移動的指標

建立前

develop → C
HEAD → develop

→
建立後

develop → C
feature/login → C

→
切換後

HEAD → feature/login
兩個 Branch 仍指向 C

建立 Branch 不會複製整份專案

Git 只新增一個 Branch Reference。Commit A、B、C 仍是同一組歷史，也不會因為建立 Branch 就多出一個 Commit。

什麼時候真正開始分岔

兩個新的 Commit 都能把 C 當成 Parent

Commit 不限制只能有一個子 Commit。Feature 建立 D、Develop 建立 E 之後，歷史自然形成兩條路徑，Branch 則標記每條路徑目前走到哪裡。

1. 建立 Commit D

Feature 上執行 git add . 與 git commit -m “Add login API”。

2. 記錄 Parent

D 的 Parent 是共同起點 C。

3. 移動 Feature

feature/login 從 C 移到 D，develop 仍停在 C。

4. Develop 也能前進

其他同事可以從 C 建立 E，兩條歷史互不覆蓋。

建立與切換可以分開，也可以一次完成

分成兩步

git branch feature/login 只建立指標；git switch feature/login 或 git checkout feature/login 才切換 HEAD。

一次完成

git switch -c feature/login 會建立 Branch 並立即切換。-c 是 –create 的縮寫。

指令 建立 Branch 切換 HEAD
git branch feature/login 是 否
git switch feature/login 否 是
git switch -c feature/login 是 是
git checkout 的角色較廣

git checkout 是較早期的指令，既能切換 Branch，也能操作檔案。git switch 把切換 Branch 的目的表達得更明確。

stash 是暫時收起尚未提交的修改

作為動詞

把某個東西藏起來，留待稍後使用。例句：I stashed some cash in my drawer.

作為名詞

私藏或儲藏的東西。例句：He has a stash of snacks in his office.

修改尚未成為 Commit

LoginService.cs 已加入登入驗證邏輯，但功能做到一半，尚未建立 Commit。

目前狀態 
git status
On branch feature/login
Changes not staged for commit:
    modified: LoginService.cs

需要先同步 Develop，但不想建立半成品 Commit

Working Tree 有修改

LoginService.cs 還在開發中。

→
git stash

暫時保存尚未 Commit 的修改，讓工作目錄恢復乾淨。

→
同步後取回

整合 develop 後，再套用 Stash 繼續工作。

Stash 底層也會使用 Commit 物件

Stash 會以特殊 Commit 物件保存 Working Tree 與 Staging Area 的狀態，並透過 refs/stash 管理。它與 Feature 上的正常開發 Commit 分開，不會推進 feature/login。

Repository 中與 Stash 有關的位置

MyProject/ ├── .git/ │ ├── HEAD │ ├── objects/ 保存 Commit、Tree、Blob 等物件 │ ├── refs/ │ │ ├── heads/ │ │ │ ├── develop │ │ │ └── feature/login │ │ └── stash 指向最新一筆 Stash │ └── logs/refs/stash 記錄 Stash 指標變動 └── LoginService.cs
這是概念示意

Git 可能把物件打包，也可能使用其他 Reference 儲存方式，因此實際檔案排列不一定完全相同。

執行前

  • feature/login → C
  • Working Tree 有未提交修改
git stash

執行後

  • feature/login 仍指向 C
  • refs/stash → S
  • Working Tree 恢復乾淨

常用 Stash 指令

檢視、套用與清理 
# 查看目前有哪些 Stash
git stash list
# 查看修改摘要
git stash show 'stash@{1}'
# 查看實際程式碼差異，-p 代表 Patch
git stash show -p 'stash@{1}'
# 套用修改，保留 Stash 記錄
git stash apply 'stash@{1}'
# 刪除指定的一筆
git stash drop 'stash@{1}'
# 刪除所有 Stash
git stash clear

兩種方式都能把最新 Develop 帶進 Feature

Merge

保留兩邊原本的 Commit，必要時新增 Merge Commit。適合已經與其他人共用的 Feature Branch。

Rebase

把 Feature Commit 重新建立在最新 Develop 後面，形成線性歷史。適合尚未與其他人共用的個人 Feature Branch。

停在 feature/login 時直接整合 
# 使用 Merge
git pull --no-rebase origin develop
# 使用 Rebase
git pull --rebase origin develop
拆成兩步更容易看清楚

git pull 會把取得遠端更新與整合連在一起。若希望先檢查遠端狀態，可以執行 git fetch origin，再選擇 git merge origin/develop 或 git rebase origin/develop。

Merge：保留分岔，再用 M 接回來

C、D、F1 與 F2 的 Hash 都保留，M 同時記錄兩條父歷史。

Rebase：把 Feature Commit 重新接到 D 後面

F1 與 F2 的修改內容會依序套用到 D 後面，形成新的 F1’ 與 F2’。

比較面向 Merge Rebase
既有 Feature Commit Hash 保留 重新建立後改變
歷史外觀 保留分岔與合併點 呈現單一路線
共用 Feature 較容易安全協作 需要先協調歷史改寫
個人 Feature 可以使用 適合整理尚未共享的歷史

共用 Branch 的關鍵是保持共同歷史

1. 建立 F1 與 F2

F1 新增登入 API，F2 新增密碼驗證，兩個 Commit 已推送到遠端 feature/login。

2. 同事取得相同歷史

同事拉下 feature/login，並以 F2 為基礎繼續開發。

3. Develop 前進到 C、D

遠端 develop 已加入新的團隊修改。

4. Feature 需要同步

此時整合方式會決定原本的 F1 與 F2 是否仍然有效。

Rebase 會建立另一組 Commit

同事的本機

F1 → F2 → F3
F3 以原本的 F2 為 Parent。

git pull –rebase
origin develop

Rebase 後的本機

C → D → F1’ → F2’
F1’ 與 F2’ 是新的 Commit。

一般 Push 通常會被拒絕

遠端仍停在原本的 F2，Rebase 後的 F2’ 不是 F2 的 Fast Forward 後繼，因此 git push origin feature/login 通常會失敗。若執行 git push –force-with-lease origin feature/login，就會改寫共用遠端 Branch 的歷史。

Merge 保留 F1 與 F2

M 同時連接 Develop 與 Feature 的歷史。原本的 F1、F2 與同事基於 F2 建立的工作不會因為同步 Develop 而失去共同基礎。

問題 Merge Rebase
會改寫既有 Feature Commit 嗎 不會 通常會
同事原本的 Commit 基礎還有效嗎 是 可能與新歷史分歧
推送到共用遠端 Feature 通常可正常 Push 可能需要 Force Push
共同開發的 Feature 較安全 需要事先協調
個人維護的 Feature 可以考慮 Rebase

如果 Feature 尚未被其他人拉取，也沒有人依賴既有 Commit，Rebase 可以讓歷史保持線性。判斷重點不是團隊人數，而是該 Branch 的歷史是否已經共享。

Rebase 讓 Feature 像是從最新 Develop 開始

原本

Develop 已前進到 C、D、E；Feature 的 F1、F2 仍從較早的共同 Commit 分出。

git rebase
origin/develop

完成後

F1 與 F2 重新建立為 F1’、F2’，依序接在 E 後面。

Rebase 後的線性歷史

查看歷史時，可以沿著單一路線從 Develop 的最新版本讀到 Feature 修改。

好處一：減少反覆同步產生的 Merge Commit

多次 Merge

F1 → M1 → F2 → M2 → F3 → M3
每次同步都可能留下新的合併節點，完整反映整合過程。

Rebase

A → B → C → D → E → F1’ → F2’ → F3’
Feature Commit 集中在最新 Develop 後面，閱讀路徑較直接。

查看 Commit Graph 
git log --oneline --graph

好處二：整理尚未共享的 Feature Commit

F1

Add login API

+
F2 與 F3

Fix login API bug
Fix typo

→
F

Implement login API

Interactive Rebase 
git rebase -i HEAD~3
同步 Develop 與整理 Commit 是兩件事

一般 Rebase 的主要作用，是把 Feature 的修改重新接到新的基礎之後。使用 Interactive Rebase 把 F2、F3 Squash 進 F1，是額外的歷史整理能力，不會在每次同步 Develop 時自動發生。

這條 Feature 歷史已經被其他人使用嗎？
是

優先使用 Merge，保留大家共同依賴的 Commit Hash。

否

可以評估 Rebase，取得線性歷史與整理 Commit 的彈性。
