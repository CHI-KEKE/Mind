BUILD · RUN · PUBLISH

.NET 的建置與發佈

專案檔描述建置需求，SDK 與 MSBuild 把原始碼整理成產物，Runtime 與網站宿主則負責讓產物真正運行。本文把這些容易混在一起的責任逐層拆開。

01 · PROJECT SDK

Microsoft.NET.Sdk 是建置規則，不是執行環境

同一套專案 SDK 可以服務不同目標框架。要判斷產物由誰執行，還要繼續看目標框架與 Runtime。

三個責任層次

建置 SDK
Microsoft.NET.Sdk 提供 MSBuild 預設屬性、檔案納入規則與建置目標。
目標框架
net462 或 net8.0 決定編譯時可用的 API 與相容邊界。
執行 Runtime
產物部署後，由相容的 .NET Framework 或現代 .NET Runtime 載入執行。

閱讀方向由上往下。SDK 負責怎麼建，目標框架決定建給誰，Runtime 負責實際執行。

<Project Sdk="Microsoft.NET.Sdk"> 裡的 Microsoft.NET.Sdk 是專案建置 SDK：它提供 MSBuild 的預設屬性、檔案納入規則與 restore／build／publish 等建置目標。MSBuild 評估專案時會隱含載入這套 SDK 的設定。它在開發或建置機器上發揮作用，不是部署到目標機器後用來執行程式的 Runtime；也不代表產物必定使用 .NET Core。

同一個 Microsoft.NET.Sdk 專案，可以用 <TargetFramework>net462</TargetFramework> 指定編譯給 .NET Framework 4.6.2，也可以用 net8.0 指定編譯給 .NET 8。能否建置還取決於所需的參考組件、套件及專案專屬 targets 是否齊全。這也說明建置用 SDK、編譯目標框架、執行用 Runtime 是三個不同層次。Microsoft：.NET 專案 SDK

專案設定 建置時使用 產物的執行目標
Sdk="Microsoft.NET.Sdk" + TargetFramework=net462 專案 SDK 的建置規則 .NET Framework 4.6.2
Sdk="Microsoft.NET.Sdk" + TargetFramework=net8.0 專案 SDK 的建置規則 .NET 8
02 · PLATFORM LINES

.NET Framework 與現代 .NET 是兩條產品線

版本數字不能跨產品線直接比較。兩者的 Runtime、基礎函式庫、應用程式模型、作業系統與部署方式都不同。

產品線演進關係

.NET Framework
4.6.2
4.7

現代 .NET

兩條橫線代表不同實作。名稱從 .NET 5 起拿掉 Core，不表示 .NET Framework 併入同一條升級路徑。

「.NET Framework」說的是程式要以哪套 .NET 平台執行

它們是不同的 .NET 實作與執行平台，不只是 Runtime 版本號不同。除了各自的執行環境，還有不同的基礎函式庫與可用 API、應用程式模型、作業系統支援和部署方式。.NET Framework 4.8 不會因為數字大於 .NET Core 3.1，就成為後者的升級版。Microsoft 從 .NET 5 起拿掉名稱中的「Core」；本文的「現代 .NET」指 .NET Core 及後續的 .NET 5+，而 .NET Framework 仍是另一條產品線。Microsoft：移轉概覽

面向 .NET Framework .NET Core／現代 .NET
執行環境 Windows 上的 .NET Framework CLR 與函式庫 .NET Core／現代 .NET Runtime 與其函式庫
作業系統 Windows 平台支援 Windows、Linux、macOS；若程式使用 Windows 專屬 API，仍只能在 Windows 執行
目標框架代號 net48、net462 等 .NET Core 常見 netcoreapp3.1；.NET 5+ 常見 net8.0 等
Web 應用程式 傳統 ASP.NET 使用 System.Web、Global.asax，常由 IIS／IIS Express 承載 ASP.NET Core 使用自己的要求處理管線與宿主；不是把傳統 ASP.NET 專案換個 TFM 就能取得
部署方式 目標 Windows 機器需具備相容的 .NET Framework 可依賴已安裝 Runtime，或將 Runtime 一起發布為 self-contained 產物

例如 SCM ApiV2 的網站使用 System.Web，目標是 .NET Framework 4.6.2。即使把它的 .csproj 轉成 SDK 格式並保留 net462，網站依舊需要原本的 ASP.NET／IIS 執行環境；如果改成 net8.0，還要移轉不相容的 API、套件與網站宿主。專案格式決定「怎麼建」，目標框架與應用程式模型決定「建給誰跑、怎麼啟動」。

03 · SDK STYLE

SDK 格式把通用規則移出專案檔

專案檔變短，是因為常見檔案納入與建置規則由 SDK 提供。套件、專案參考與特殊行為仍然存在。

舊式專案檔與 SDK 格式的資訊分工

舊式 .csproj
  • 逐一列出原始碼
  • 明列 imports 與參考
  • 建置樣板重複出現
SDK 提供預設規則
  • 遞迴納入一般 .cs
  • 處理常見資源檔
  • 排除 bin 與 obj
精簡後的 .csproj
  • 目標框架
  • 套件與專案參考
  • 專案特有設定

箭頭表示責任移轉，不表示依賴消失。SDK 格式仍須明確描述專案特有需求。

SDK 省掉的是重複的檔案清單與通用建置樣板，沒有取消依賴關係。需要特殊納入或排除規則時，仍可在 .csproj 明確設定。

「SDK 格式」說的是 .csproj 如何描述建置工作
SDK 格式專案也可以指定 net48，編譯給 .NET Framework 4.8 使用。

舊式 .csproj 常把每個原始碼檔案逐一列出，例如 <Compile Include="Program.cs" />。新增或搬移檔案時，專案檔也可能要跟著更新。SDK 格式把常見規則交給 SDK：<Project Sdk="Microsoft.NET.Sdk"> 讓 MSBuild 自動載入 SDK 的建置設定；預設以遞迴規則納入專案目錄下的 .cs 檔，也處理常見資源檔，並排除 bin、obj 等輸出目錄。於是 .csproj 主要留下目標框架、套件參考、專案參考及特殊設定。

比較面向 SDK 格式專案 常見的舊式 .NET Framework 專案

目標框架寫法 常用 <TargetFramework>net8.0</TargetFramework>；也可寫 net48 常用 <TargetFrameworkVersion>v4.8</TargetFrameworkVersion>
常見工具入口 dotnet restore、dotnet build、dotnet publish Visual Studio 的 MSBuild.exe；套件還原須看 PackageReference 或 packages.config

04 · MIGRATION GATES

刪除檔案清單只是轉換的第一步

傳統 ASP.NET 網站還有內容檔、輸出路徑、Web targets 與設定轉換。每一項都必須通過驗證，才能判斷轉換是否保持原有行為。

舊專案轉成 SDK 格式的驗證閘門

1
目標框架v4.6.2 改寫為 net462，執行平台仍是 .NET Framework。
保持相容邊界
2
內容與資源檢查預設納入是否重複，發布用途是否完整保留。
核對交付內容
3
輸出路徑確認 IIS 仍能從預期的 bin 位置載入網站組件。
核對宿主讀取位置
4
網站專屬 targets保留或替代 Microsoft.WebApplication.targets 與 SlowCheetah 行為。
核對建置與轉換
5
啟動與請求用 IIS 或 IIS Express 啟動網站，檢查請求與發布產物。
證明可以運行

.csproj 的 SDK 格式可以視為「建置規則的預設套件」。它可以自動找出專案目錄裡一般的 .cs 檔，省去逐筆寫 <Compile Include="...">。然而，它不知道舊版框架專案原本如何處理 IIS、內容檔、設定轉換與發布，因此「不用列出每個 .cs」和「其他建置行為完全相同」是兩件事。

SCM ApiV2 原本的設定 只加 Sdk、刪 .cs 清單之後還要確認什麼
<TargetFrameworkVersion>v4.6.2</TargetFrameworkVersion> 改用 SDK 格式的 <TargetFramework>net462</TargetFramework>，執行目標仍是 .NET Framework 4.6.2
專案明列內容檔、資源檔與 packages.config SDK 也會預設納入部分檔案；要檢查是否重複、是否保留原本的發布用途
網站組件輸出到 bin\ SDK 可能在輸出路徑附加 net462；要確認 IIS 讀到的仍是預期的網站組件
匯入 Microsoft.WebApplication.targets，另有 SlowCheetah 設定轉換 要驗證這些原有建置目標和 SDK 預設目標能否共同運作，且轉換後的設定檔正確

所以合理的預期是一般 .cs 檔案清單可以刪，但網站專屬設定仍須逐項比對。 即使編譯成功，也要再用 IIS／IIS Express 啟動網站，檢查實際請求與發布產物，才能說「轉換後照常運作」

05 · COMMAND FLOW

Restore 準備材料，Build 產生組件，後續工作再分流

Run、Test 與 Publish 都可能觸發所需的前置建置。跳過前置步驟時，目標框架、組態與 RID 必須保持一致。

第二條線表示三種不同目的，不代表 Run、Test、Publish 必須依序執行。

這是概念順序，一般 SDK 專案的 dotnet build 預設會 restore，而 dotnet run、dotnet test、dotnet publish 也會執行各自需要的前置步驟。若前置步驟已完成，可視情況使用 --no-restore、--no-build，但目標框架、組態、Runtime Identifier（RID）等條件須一致

Solution 組織專案，專案檔描述每個建置單位

.sln 管理多個專案的集合與組態，.csproj 則記錄單一專案的目標框架、參考與輸出。

Solution 與專案檔的責任關係

.csproj 指定目標框架、套件參考、專案參考、輸出類型等建置屬性；.sln 組織多個專案

07 · BUILD ENGINE

MSBuild 評估設定，再執行 targets

命令列參數會改變本次建置屬性。SDK 提供規則，目標框架限定 API，Runtime 則在部署後執行產物。

圓形代表建置引擎。左右兩側是輸入與輸出，Runtime 不在這個建置引擎內。

MSBuild 評估這些設定，並執行對應的 targets。對 SDK 專案，dotnet build 使用 .NET SDK 內的 MSBuild，大致相當於 dotnet msbuild -restore。-c Release、-r win-x64、-p:Name=Value 等參數會改變這次建置的屬性。

08 · RESTORE

Restore 解析依賴，讓後續 Build 知道材料在哪裡

還原不會替專案新增或升級套件。它讀取既有需求、解析完整依賴、尋找檔案，再寫下可供建置使用的結果。

Restore 的四個資料處理階段

讀需求專案、目標框架、來源設定
算依賴版本、相容性、依賴圖
找檔案先查快取，缺少才連來源
記結果快取與 project.assets.json

兩種套件參考格式對應不同還原路徑

PackageReference

dotnet restore

Restore 的意思是依照專案已記錄的套件需求，把建置材料備齊，流程依序是

  1. 讀需求：評估 .csproj、ProjectReference、目標框架與 NuGet 來源設定（nuget.config），找出直接依賴的套件
  2. 算完整依賴：解析套件彼此需要的其他套件、版本與目標框架相容性，得到可供建置的依賴圖
  3. 找檔案：檢查本機快取，缺少時才向設定的 NuGet 來源取得，因此可能需要網路、內網連線或認證
  4. 記結果：PackageReference 專案通常將套件放在全域套件快取，並產生 obj\project.assets.json，讓後續 build 知道實際使用哪些套件組件。Restore 不會新增或升級專案檔裡的套件參考

為什麼新版專案用 dotnet restore，舊版專案用 nuget restore？

關鍵是套件參考格式，不是「.NET Core 可以、.NET Framework 不可以」，例如 Livebuy API 是 Microsoft.NET.Sdk.Web、目標 net8.0，在 .csproj 用 PackageReference 記錄套件，而 SCM ApiV2 網站則用 packages.config 記錄套件，例如 Autofac 4.1.1，並在 .csproj 用 HintPath 指向 solution 的 packages\Autofac.4.1.1\... DLL

專案 套件需求寫在哪裡 合適的還原入口 還原後要看到什麼
Livebuy API .csproj 的 PackageReference dotnet restore；或讓 dotnet build 隱含還原 全域套件快取有套件，專案產生 obj\project.assets.json
SCM ApiV2 各專案的 packages.config，搭配 .csproj 的 HintPath nuget restore 或支援版本的 Visual Studio MSBuild 明確啟用 RestorePackagesConfig=true solution 的 packages 目錄有對應版本，HintPath 找得到 DLL

dotnet restore 主要處理 .csproj 裡的 PackageReference，不會替舊專案還原 packages.config 所列的套件，因此對專案例如 SCM ApiV2 執行這個指令，可能在評估舊式專案時失敗，也可能結束卻沒有補齊 packages 目錄，無法只看指令執行結束，就認定原建置依賴已備齊

另外 nuget restore 不是只能處理 packages.config，也能處理部分 PackageReference 專案，只是對 SCM ApiV2 的現況，它是合適的選擇

若本機已有全部套件，還原可能不需重新下載，若缺少套件新舊專案都可能從網路拉取，如果來源無法存取，都可能因網路或認證失敗

09 · BUILD

Build 是協調工程，編譯只是其中一道工序

MSBuild 先評估專案與相依順序，再執行還原、資源處理、設定轉換、編譯與輸出複製。成功只代表指定條件下完成建置。

Build 的工作邊界

MSBuild 協調
評估專案
安排相依順序
執行 targets
整理輸出
其中的編譯工序
原始碼與參考
語法與型別檢查
產生 IL
DLL 與 PDB

兩條泳道是包含關係。編譯位於 Build 內部，並不涵蓋所有建置工作。

Build 的核心是 MSBuild 讀取 .sln / .csproj，找出專案間的先後順序，載入專案指定的建置規則，再編譯、複製輸出。 規則也可能包含產生程式碼、處理資源檔及執行自訂工作。Build 成功表示指定條件下能編譯

Build 與「編譯」的差異：C# 到 DLL 中間發生什麼？

C# 原始碼到執行時機器碼

C# 原始碼類別、方法、運算式
語法與語意名稱、型別、參數、參考
IL 組件DLL、metadata、可能的 PDB
Runtime 與 JIT程式啟動後才轉成機器碼

app.Run() 與 Application_Start() 在 Build 階段只會被編譯，不會真正執行。

Build 是總工程；編譯是其中把原始碼轉成組件的一道工序。

前述 restore、決定建置順序、處理資源與內容檔、設定轉換、複製輸出，都屬於 build，並非 C# 編譯器本身負責。MSBuild 在需要編譯時，把 .cs 檔、目標框架的參考組件、NuGet 和其他專案的參考，交給 C# 編譯器

編譯階段 具體在做什麼 用兩個專案理解
讀取與解析 將 .cs 內容辨識成類別、方法、運算式等語法結構 讀到 Livebuy 的 WebApplication.CreateBuilder(args)；讀到 SCM 的 WebApiApplication : System.Web.HttpApplication
語意與型別檢查 確認名稱、型別、方法、參數和參考組件能對上；錯誤會在此報出 Livebuy 要找得到 ASP.NET Core 的 WebApplication；SCM 要找得到 .NET Framework 的 System.Web.HttpApplication
產生組件 將程式碼轉成 IL（中介語言），連同類別、方法與參考的中繼資料寫進 DLL；視設定產生 PDB 供除錯 兩者都可得到 DLL，但各自針對不同目標框架，不能只看副檔名判斷可否互換

DLL 裡的一般受控程式碼主要是 IL，並非按下 build 時就全部變成目標 CPU 的機器碼。 等程式真的啟動、Runtime 載入組件並執行方法時，通常由 JIT 將需要的 IL 轉成機器碼。因此 Livebuy 的 app.Run()、SCM 的 Application_Start() 在 build 階段都只是被編譯，沒有真的執行。特定發布方式可能另做預先編譯；此處描述兩個專案的一般 build 流程。

dotnet build 與 Visual Studio MSBuild.exe 是什麼關係？

同一種建置技術，兩套啟動環境

dotnet build.NET SDK 內的 MSBuild
適合目前案例Livebuy 的 Microsoft.NET.Sdk.Web
MSBuild.exeVisual Studio 與已安裝建置元件

分支依據是專案需要的 SDK、targets 與建置元件，不是單看 DLL、IIS 或 Framework 名稱。

Microsoft.NET.Sdk.Web 是專案 SDK，不是一般 NuGet 套件，也不是 Web Server。Livebuy API 的 .csproj 第一行指定它，目標框架是 net8.0；dotnet build 啟動 SDK 內的 MSBuild，MSBuild 再載入該 SDK 的屬性與 targets，依 ProjectReference 建置相依專案，最後產生 API 的組件。dotnet build 大致相當於 dotnet msbuild -restore，所以還原通常包含在這次操作中。

舊版專案建置

SCM ApiV2 的 Web 入口則是舊式 .csproj，目標 v4.6.2，匯入 Microsoft.WebApplication.targets，並使用 System.Web、Global.asax。這個網站模型執行時由 IIS／IIS Express 承載；它選擇 Visual Studio MSBuild.exe 的直接原因，則是建置時需要傳統 ASP.NET 的 Web Application targets 與 .NET Framework 版 ASP.NET 編譯工具，並非「凡是用 IIS 就必須用 MSBuild.exe」。Microsoft 對用 dotnet 建置這類網站的 MSB4249 錯誤有明確說明。

這裡要分清專案型態與直接的工具限制。採用傳統 ASP.NET Web Application 是上游原因：它需要網站專屬的編譯、內容處理等行為；.csproj 因此匯入 Microsoft.WebApplication.targets 等規則。這些規則及其使用的 .NET Framework 版 ASP.NET 編譯工具，才是目前不能直接用 dotnet build 取代的技術原因。專案檔沒有一個單純寫著「只能用 VS MSBuild」的開關。

所以刪掉 WebApplication.targets 的匯入，不等於完成工具轉換：如果原本的網站編譯或內容處理行為隨之消失，即使某次編譯成功，也不能據此認定網站能照常啟動與發布。要改用另一套建置入口，必須先找出並保留或替代這些行為，再實際驗證。

因此，對目前包含 Web 入口的整個 SCM ApiV2 solution，不能把 dotnet build 當成 Visual Studio MSBuild.exe 的直接替代：前面還有 packages.config 還原差異，後面有傳統 ASP.NET 網站編譯差異。它可能先在還原或專案評估階段失敗；即使套件已備齊，也可能在網站建置階段失敗。這不表示 .NET Framework 類別庫一律不能用 dotnet build，也不表示 Visual Studio MSBuild.exe 不能建置 SDK 格式專案；要看具體專案需要的 targets 與建置元件。

常見編譯產物在 bin\<Configuration>\<TargetFramework>\，包含 DLL、可能的 EXE、PDB、.deps.json、.runtimeconfig.json 等，obj\ 放中間產物與還原資訊。這是 SDK 專案的常見版面，而 SCM ApiV2 Web 專案明定輸出到 bin\。實際檔案與路徑以專案設定為準

Livebuy 由應用程式自己的入口建立宿主；SCM ApiV2 則先由 IIS Express 或 IIS 接收流量，再讓 ASP.NET 載入網站組件。

誰提供啟動入口、誰承載網站

啟動入口是「程式從哪段程式碼開始執行」
網站宿主是「哪個持續運行的程序接收 HTTP 請求，並讓網站程式處理它」。DLL 只是組件的檔案形式，不能只看副檔名判斷能否 dotnet run

問題 Livebuy API SCM ApiV2 WebSite
程式從哪裡開始？ Program.cs 建立 WebApplication，最後呼叫 app.Run() 由 IIS／ASP.NET 載入網站；網站初始化時呼叫 Global.asax.cs 的 Application_Start()
誰接收 HTTP 請求？ dotnet run 啟動應用程式後，ASP.NET Core 的 Web Server（一般為 Kestrel）在程序內監聽 IIS Express（本機開發）或 IIS（部署環境）先接收，再交給傳統 ASP.NET 管線
可以直接用 dotnet run 嗎？ 可以，指定 Web API 的 .csproj 目前的 WebSite 是 OutputType=Library，不能把它當成可直接啟動的程式

注意：dotnet run 針對單一可執行專案，不會像 dotnet build 一樣把 .sln 當成要執行的程式。dotnet run 是開發時的啟動方式；正式部署應使用 publish 產物與適合的宿主設定。

IIS Express 是什麼？它是一個 App 嗎

沒錯，IIS Express 是會實際運行的 Web Server 程序（iisexpress.exe），可把它理解成偏向本機開發與測試的輕量版 IIS。Visual Studio 可啟動它並指定網站目錄與監聽位址。它負責接收 HTTP 流量、依網站設定選擇處理管線、將請求交給 ASP.NET 網站程式並送回回應

SCM ApiV2 Web 專案記錄了 UseIISExpress=true 與 http://localhost:2558/。這是專案中的本機設定，實際位址可能被本機 Visual Studio 設定覆蓋。正式環境通常由 IIS 承載，兩者都是網站宿主，但 IIS Express 主要用於開發與測試

  4. 補齊容器需要的檔案： Dockerfile 再把 .manifest、releng.json 放進 /out/.manifest，把前端的 dist 放到 /out/wwwroot。因此最後交付的內容不只有 dotnet publish 的原始輸出，還包含後續複製進去的檔案。
  5. 製作可執行映像： 最後一階段改用 ASP.NET Runtime 映像，把 /out 複製到 /app，並設定 CMD dotnet /app/${NYS_FQDN}.dll。Docker 映像建置完成，表示程式與執行環境已封裝；容器真正被啟動時，這條 CMD 才會執行，Livebuy 的 Program.cs 才會建立並啟動網站。
  6. 交給部署流程： 映像之後是否推送到 registry、由哪個工作部署到 Kubernetes、如何驗證站台可用，取決於引入的共用 Pipeline 範本與部署設定；這些步驟不在目前檢視到的 repo 內完整展開。因此要把「dotnet publish 成功」、「Docker 映像建置完成」和「站台已對外服務」視為三個不同完成點。

GitLab CI → 共用範本選擇 Docker 建置 → dotnet restore → dotnet publish 到 /out → 補入前端／中繼資料 → 封裝 Runtime 映像 → 部署並啟動容器（外部範本決定）

Artifact 產生與 Deploy(...) 的細節依賴外部串接，圖中只呈現目前檔案可以證明的責任交接。

SCM ApiV2 是 .NET Framework 4.6.2 的傳統 ASP.NET Web Application，Microsoft.WebApplication.targets 提供 Web 專案建置／發佈流程，.pubxml 提供本次發佈的參數。.pubxml 不是發佈引擎，發佈也不需要開啟 Visual Studio IDE；執行它的是具備 Web 建置元件的 Visual Studio 系列 MSBuild.exe。 以下依 Jenkinsfile、JenkinsfileDeploy、build.ps1、build.cake 和 QA 發佈設定檔說明，同樣沒有實際執行。

  1. 發動： Jenkinsfile 指定在標記為 msbuild 的節點執行。符合條件時，Build 階段呼叫 ./build.ps1 -Target Build；JenkinsfileDeploy 也提供另一條帶市場、部署批次等參數的路徑。build.ps1 是 Cake 啟動器，最後交由 build.cake 執行指定任務。
  2. 還原與建置： Cake 的 Build 任務先依賴 Nuget Restore，對 solution 執行 NuGetRestore(...)後執行 Msbuild 任務。這也對應網站專案的 packages.config 與傳統 NuGet 套件還原方式
  3. 建置時同時發佈： Msbuild 任務對 NineYi.Scm.ApiV2.sln 呼叫 MSBuild，設定 DeployOnBuild=true、PublishProfile=NineYi.Scm.ApiV2.QA.Deploy.pubxml、建置組態，以及 publishUrl，MSBuild 編譯各專案後，依 Web Application targets 啟動網站發佈流程，QA profile 指定 WebPublishMethod=FileSystem，也有額外納入 bin/*.xml 的規則，publishUrl 由 Cake 依環境組成，通常落在 D:\Archives\<MachineKey>\NineYi.Scm.ApiV2，因此此階段的「發佈完成」是網站檔案已整理到指定目錄
  4. 準備環境檔與交付物： build.cake 另外定義 Copy Config，可將基底 AppSettings 複製並套用環境／市場轉換；Deploy Artifact 任務會接著封存網站目錄並上傳 artifact。但目前看到的兩份 Jenkinsfile 只明確呼叫 Build、Test、Deploy，沒有直接呼叫 Deploy Artifact。 因此 artifact 由哪個外部工作產生、是否會在每次流程執行，不能只由這些檔案確認
  5. 部署到機器： Jenkins 的 Deploy 階段呼叫 Cake 的 Deploy 任務。Deploy to machines 會依環境與市場下載 artifact、解壓縮，再對符合市場的目標機器呼叫 Deploy(...)，目標是該機器的網站共享路徑。這個 Deploy 函式來自外部 Cake 函式庫，備份、複製及 IIS 操作的更細節，需要追該函式庫或執行紀錄才能確認
  6. 網站開始服務： 當檔案已部署、IIS 網站與應用程式集區設定正確，IIS 的工作行程才會載入網站組件，ASP.NET 才會在網站啟動／請求到來時執行 Global.asax 的初始化流程。MSBuild 發佈成功不代表 IIS 已載入新版，也不代表健康檢查已通過。

速記：Jenkins → build.ps1／Cake → NuGet restore → VS MSBuild 建置＋FileSystem 發佈 → artifact／環境設定（需核對外部串接）→ 部署到 IIS 機器 → IIS 載入網站並接收請求。

這兩條流程最重要的差別：Livebuy 把 dotnet publish 產物放入 ASP.NET Runtime 容器映像，由容器啟動程式；SCM ApiV2 用 VS MSBuild 的 Web 發佈流程整理網站檔案，再由 IIS 承載網站。
