時間模型

下午三點，滑鼠停在曲線上中午十二點的那個點，跳出一個數字：12。右上角明明選了 Last 6 hours，這 12 筆是六小時的總數，還是中午前那一小時的紀錄？

故事從右上角開始。Last 6 hours 把畫面拉到約 09:00～15:00，像翻開這六小時的值班紀錄。它讓中午那個點出現在眼前，但還沒有告訴我們，點上的 12 是怎麼算出來的

接著看圖上的點怎麼排。如果 Query options 的 Interval，或查詢的 Step，設為 1h，圖表就大約每小時留下一個點：09:00、10:00、11:00、12:00……。這決定的是多久算一次

真正替那 12 筆劃出範圍的，是查詢裡的 count_over_time(…[1h])。[1h] 讓十二點的點回頭看約 11:00～12:00，所以 12 代表的是這一小時的筆數。右上角即使展示六小時，也不會把十二點的點變成六小時總數

輪到 Alert 時，又多了兩個時鐘。30m to now 說的是「這次評估要拿哪段查詢結果」，假設現在 15:00，Range Query 約取 14:30～15:00 的一串點，每個點仍照查詢中的 [1h] 各自往前算。Alert evaluation interval = 1m 則表示 Grafana 約每分鐘重新問一次「現在符合條件嗎？」它不會把 [1h] 改成一分鐘。

最後試著把 Step 從一小時改成十五分鐘。十二點的點回看 11:00～12:00，12:15 的點回看 11:15～12:15；兩段紀錄重疊了四十五分鐘。同一筆 log 可能同時被兩個點算進去。曲線可以拿來看變化，卻不能把沿途的點直接相加，當作整段期間的總筆數。

現在把這些時間設定放進同一個現場。假設 11:00～12:00 有 12 筆 log，下午又分別在 14:05、14:20、14:35、14:50 各出現 1 筆。為了看清 Alert 如何選值，以下示意 Dashboard 和 Alert 的查詢點都剛好每 15 分鐘對齊；Alert 另外使用 Range、Reduce Last、門檻 > 3、Pending 0。這些是教學用的假設，不是某條實際規則的設定。

Interval、Min. Interval 與 MD

同一張趨勢圖，縮在 Dashboard 的角落時看起來很平順；點開放大，細小的起伏又冒出來了。資料沒有換，Grafana 只是換了「隔多久取一個點」的間距。這個間距，就是 Query options 裡看到的 Interval。

Grafana 會參考畫面寬度和所選的時間範圍，自動估算適合的 Interval。假設目前算出 1m，意思是圖上約每分鐘取一個點。畫面變窄或把時間拉長，點可能排得更疏，Interval 也會跟著變；畫面上那個數字不一定是事先寫死的設定。

那麼，Min. Interval = 15s 又在做什麼？它替自動計算畫一條底線：點的間距不要比十五秒更密。底線不是指定值，所以 Grafana 仍可能選 1m、5m 或更大的間距。

MD = 43200 的全名是 Max data points。它談的是每條序列可回傳的點數與查詢解析度。若查詢真的會回傳太多點，資料來源可能再依支援的方式縮減。面板大小也可能影響自動間距，因此改變看到的線條細節

最後還有一個容易混在一起的時間概念，查詢若明確設定 Step = 1m，那是要求每分鐘算一個點；count_over_time(…[1h]) 裡的 [1h] 仍讓每個點各自回看一小時。點變密了，回看的窗口沒有縮短。

現在 15:00，畫面看最近六小時，假設面板寬度使 Grafana 自動選出 Interval = 1m，查詢的每點窗口固定為 [1h]。實際自動值與點的對齊仍以當時面板和資料來源為準。

畫面或查詢走到哪一步 設定或時間 會發生什麼

Grafana 安排查詢點 示意自動算出 Interval = 1m 約每分鐘取一點，六小時大約是 360 個間隔，含兩端約 361 個點

Range、Instant 與狀態轉換

下午 13:30 發生一筆錯誤，到了 14:44，Alert 要回答的問題，可以有兩種問法

「現在回頭看一小時，還有錯誤嗎？」

或者

「最近半小時算出的那串結果，曾經出現錯誤嗎？」問法一變，即使查的是同一筆 log，答案也可能不同

如果只想知道評估當下往前一小時的筆數，Instant 很直接。查詢裡的 count_over_time(…[1h]) 在 14:44 看約 13:44～14:44；13:30 的錯誤已經離開窗口，結果是 0。Alert 畫面即使還顯示 30m to now，固定寫在查詢中的 [1h] 也不會被改成半小時，Instant 更不會因此自動產生一整串點

如果問題是「最近半小時的變化如何」，就選 Range。30m to now 讓這次評估拿到約 14:14～14:44 的多個查詢點。每個點依然各自用 [1h] 往前數；早一點的窗口還包著 13:30，晚一點的窗口則已經放開了它。這時不能只說「Range 有資料」，還得看後面怎麼把一串值收成一個答案

選 Reduce Last，看的是最後一點，這個例子得到 0；如果本來只關心最新值，Instant 通常更容易表達。選 Reduce Max，看的則是整串結果裡最高的那一點，這裡得到 1。Max 回答的是「這段結果曾否非零」，並不是把半小時的數字加總。

把時鐘撥回 14:44，完整走一遍，目前只有 13:30 那一筆錯誤，並假設查詢在沒有符合的 log 時用 or vector(0) 回傳數值 0，Range = 30m to now、Step = 5m、每點窗口 [1h]；比較門檻暫設 > 0，Pending 暫設 0

Evaluation、Pending、Keep firing for

13:30 的那筆錯誤已經被查到了，Alert 卻不一定立刻響起。它還要看，這個條件是偶爾出現一下，還是持續了一段時間。這時登場的是三個設定：多久檢查一次、要連續異常多久、恢復後又要觀察多久。

Evaluation interval 是檢查的節奏。設 1m，Grafana 就約每分鐘重跑查詢並重新判斷一次；這和圖表 Query options 的 Interval 各管各的。Pending period 則像一段觀察期。第一次符合門檻先從 Normal 進 Pending，持續符合到設定時間才進 Alerting；中途只要有一次不符合，就回 Normal。若設為 0，第一次符合就能進 Alerting。

已經進入 Alerting 之後，情況好轉了，還有 Keep firing for。它讓狀態先進 Recovering，確認恢復維持到設定時間，才轉 Normal／Resolved；期間若重新超標，就回 Alerting。設為 0 時，評估確認恢復即可解除。狀態仍是在評估時更新：每五分鐘才評估一次，即使 Keep firing for 只設一分鐘，也不會在沒有評估的那一分鐘自動確認恢復。

沿用上一分頁的單筆錯誤，看看這三個時間怎麼接力。以下全部是數值模擬：錯誤發生在 13:30，規則每分鐘評估；門檻是結果 > 0，Pending 設 5m、Keep firing for 設 10m；Query 在沒有符合 log 時仍回傳數值 0。Range + Max 會讓較早的非零點留在最近半小時的結果裡，直到約 15:00 才不再符合。右欄另外比較改用 Instant + [1h] 時的時間線；實際查詢點對齊與狀態轉換仍以規則設定為準。

No data

錯誤消失後，監控畫面安靜了。這個安靜可能有兩種意思：查詢成功，明確算出 0 筆；或是查詢根本沒有回傳任何數值。對 Grafana Alert 來說，兩者走的是不同的路。

例如 Loki 的 sum(count_over_time(…[1h]))，完全沒有符合的 log 時，可能回傳空的 series，而不是數值 0。若規則設 No data → Normal，Grafana 會依這個設定處理狀態；它不是「先等 Keep firing for，確認持續恢復」的數值路徑。若要讓整個服務的合計在沒有匹配 log 時明確回傳 0，可以寫成： 

sum(count_over_time(
  {service="prod-promotion-service"} |= "錯誤" [1h]
)) or vector(0)

or vector(0) 適合這種合計為單一數字的情境。若查詢改成 sum by (pod) 或 sum by (jobname)，它不會替每個消失的 Pod 或 Job 各補一個 0。這時要再分辨：整個查詢都沒有資料，是 No Data；查詢仍有其他 Pod，只少了一個 Pod，是 Missing Series。查詢 timeout 或失敗則是 Error，vector(0) 也無法把失敗變成正常的 0。

再看多維度規則。若 sum by (pod) 回傳 Pod A、Pod B，Grafana 可以替兩個 Pod 分別判斷，A 是 Normal、B 是 Alerting；只用 sum(…)，則把數值合成整體再判斷。當某個 Pod 消失時，Missing series evaluations to resolve = 2 表示它連續缺席兩次評估後，舊的 alert instance 才被視為 stale、解除並移除。Pod 被替換也可能造成這種缺席。

因此畫面顯示 Normal，仍要回頭查原因：數值確實恢復、No Data 被設成 Normal、查詢錯誤被設成 Normal、某個 series 消失，或規則剛被修改，都可能讓狀態改變。State history 與 grafana_state_reason 可以協助辨認；No Data／Error 設為 Normal 時，走的是設定的狀態處理，不是一般門檻恢復的 Keep firing for 流程。

把「0、整體無資料、只少一個 Pod、查詢失敗」排在一起看。下表是模擬：每分鐘評估，門檻暫設 > 3、Pending 設 0、No Data／Error 都設 Normal，Missing series 次數設 2。前兩列使用單一合計值，後面改用依 Pod 分組的查詢；兩種 Query 是用來比較行為，並非同一條線上規則同時切換。

查詢與時間 回傳情況 Grafana 走哪條路 畫面該怎麼讀
整體合計，15:00 明確回傳數值 0 正常比較門檻，0 > 3 為假 Normal 是一次有數值的判斷
整體合計，15:01 查詢成功，卻沒有任何 series 走 No Data → Normal 的設定 同樣顯示 Normal，但沒有證明錯誤數是 0
依 Pod 分組，15:02 Pod A = 2、Pod B = 5 A 正常，B 因 5 > 3 進 Alerting 一條規則有兩個 alert instances

實際案例 1：MY Prod Cart-Service 的 Ingress 成功率 Alert

MY Prod 的購物車入口還在回應請求，成功率卻慢慢往下掉。Alert 要抓的不是「曾經失敗過一次」，而是成功率是否持續低於 80%。先看它如何把每一筆請求換算成一個比例： 

sum by (ingress) (
  rate(nginx_ingress_controller_requests{
    status!~"[4-5].*", exported_namespace="prod-cart-service"
  }[2m])
)
/
sum by (ingress) (
  rate(nginx_ingress_controller_requests{
    exported_namespace="prod-cart-service"
  }[2m])
)

分母是全部請求速率；分子排除狀態碼以 4、5 開頭的請求，所以這裡的「成功」依查詢定義也包含 3xx 等狀態碼。兩邊各自按 ingress 分組，再相除。結果 0.75 就是 75%，每個 ingress 都有自己的數值與 Alert instance。

有了比例，還要問「拿哪個時間的比例來判斷」。查詢 A 取最近 15 分鐘的一串點，串中每一點用 [2m] 回看前兩分鐘；B 只取最後的有效值，C 再比較是否 < 0.8。規則每分鐘重跑一次，低於門檻要持續三分鐘，才真的進 Alerting。

查看完整規則設定
設定 本例的值 意義
A 的 Query type Range 每次評估取最近 15 分鐘的一串成功率點
A 的 Relative time range 15m to now 決定這串點的時間範圍，不是「成功率統計 15 分鐘」
PromQL 的 [2m] 2 分鐘 每個點各自往前 2 分鐘計算 rate
A 的 intervalMs／maxDataPoints 15000／43200 查詢採樣相關參數；不是 Alert 每 15 秒評估，也不是一定產生 43,200 點
Evaluation group interval 1 分鐘 Grafana 約每分鐘重新執行 A → B → C
B：Reduce Last，忽略非數值 每個 ingress 只拿這串點最後一個可用數值
C：Threshold < 0.8 B 的值低於 80% 才符合門檻；恰好 80% 不符合 <
Pending period 3 分鐘 持續符合門檻約 3 分鐘後才由 Pending 進 Alerting
Keep firing for 0 秒 條件恢復時，不另等 Recovering 時間

規則資料中的 B、C 也帶有 relativeTimeRange: 1h to now，但它們只是處理 A 的結果，A 實際查詢範圍仍是 15 分鐘。intervalMs = 15000 和 maxDataPoints = 43200 是查詢採樣參數，也不代表 Alert 每十五秒評估一次。

狀態確認後，通知才開始計時

這條規則另外設定了通知節奏：Group wait = 5s、Group interval = 30s、Repeat interval = 1m。它們在 Alert 進入 Alerting 後才接手，不會縮短三分鐘的 Pending。新群組先等五秒再送第一則通知；後續群組若有新增或解除的 Alert，以三十秒的週期處理變化；如果群組沒有變化、仍在 firing，約一分鐘後才考慮重送提醒。實際通知還受路由與群組排程影響。

設定 控制的事 本例
Evaluation interval 多久重新執行查詢與條件判斷 每 1 分鐘
Pending period 條件持續符合多久，才從 Pending 進入 Alerting 3 分鐘
Keep firing for 條件恢復後，Alert 還要維持 firing 多久 0 秒；下一次確認恢復時可轉 Normal／Resolved
Group wait 新通知群組成立後，首次發送前等待多久 5 秒；期間可合併其他 Alert
Group interval 首次通知後，檢查群組是否有新增或解除的 Alert，並通知變化的週期 30 秒
Repeat interval 群組沒有變化且仍有 firing Alert 時，隔多久重送提醒 1 分鐘；依 Group interval 的週期檢查

這裡最要分開的是 Repeat interval 與 Keep firing for。前者問「還在 firing 時，多久再提醒一次？」後者問「條件恢復後，多久才解除？」這條規則 Keep firing for 設 0，所以評估確認跨過恢復門檻 > 0.8 時，就可轉 Normal／Resolved；解除通知屬於群組變化，不是 Repeat 提醒。

從成功率下降走到通知

實際案例 2 ：Shopping Service Exception Alert

購物服務偶爾出現一筆例外，不一定值得立刻驚動值班人員；同一種錯誤密集出現，情況就不同了。這條規則想抓的，正是「最近十分鐘內，某一種例外訊息是否超過三十筆」。

它先從 prod-shopping-service 的 shopping-web-api、exception_logs 撈 log，排除「購物車資料過期」與兩種點數錯誤，再用 JSON 解析 _ext 與 _msg。sum by (_ext, _msg) 把例外類型與完整訊息都相同的 log 放在一起。因此同一類型若帶著不同訊息，會分開計數。尾端的 or on() vector(0) 只在整個查詢沒有匹配序列時補 0，並不會替每個消失的訊息組合各補一個 0。

時間接著分成三層。Evaluation group Shopping5mQuery10m 每五分鐘重新評估；Query A 的 Range 是 10m to now，會取一串點；串中的每一點又用 count_over_time(…[10m]) 各自回看十分鐘。條件 B 是 Classic condition，對每組結果取 Last，只要有一組 > 30 就觸發。Classic condition 最後只形成一個 Alert instance，不會每種例外訊息各送一個 Alert。

Pending 與 Keep firing for 都設為 0。也就是說，評估時首次發現某組超過三十筆，就可進 Alerting；下一次評估確認條件不成立，就可解除。No Data 與查詢 Error 都設為 Normal，看到 Normal 時仍要區分是數值真的下降，還是走了無資料或錯誤的設定。

這條規則沒有自行覆寫通知時間。匹配的通知路由送往 #shopping-rd-sg-maintain，Group wait 是五秒、Group interval 是三十秒；該路由沒有顯示 Repeat interval 的覆寫值。這些是通知的節奏，並不會讓規則改成每三十秒評估一次。

沿著同一組 _ext、_msg 看三次評估。下表的筆數是模擬，時間假設剛好落在整五分鐘；每列都重新查詢，而相鄰的十分鐘窗口會重疊五分鐘，不能把 29、31、20 加起來當作總數。最後兩列另外假設把 Keep firing for 改成一分鐘，只用來看評估頻率的影響，不是這條規則目前的設定。

實際案例 3 ：Promotion Service Exception Alert 的 Range 與 Last

這條 Promotion Alert 的名字寫著「30 秒間隔」，查詢畫面裡卻同時出現 1h to now 和 [30s]。三個時間放在一起，看似互相拉扯，其實各有工作：每三十秒重新評估，每次取最近一小時的一串結果，而串中的每個點只回看三十秒 log。

查詢 A 從 Promotion Service 的 exception log 計數，條件 B 使用 Classic condition：每條結果序列取 Last，只要有一條 > 10，就符合門檻。Pending 和 Keep firing for 都設 0；No Data、查詢 Error 都設為 Normal。這條規則沒有自行設定通知時間；匹配的路由送往 #promotion-service-rd-sg-maintain，Group wait 為五秒、Group interval 為三十秒，沒有顯示 Repeat interval 覆寫值。通知的三十秒與評估的三十秒是兩個不同計時器。

現在沿著一次評估往回走。假設 15:00:00 開始，A 取約 14:00～15:00 的查詢點。最早的點若也要往前數三十秒，Loki 可能得讀到約 13:59:30 的 log；但這不是把一小時的 log 全加成一個數字。B 只看各條序列的最後可用值，不會把沿途的 12、15、8 相加，也不是挑最大的 15。

這裡還有一個值得先看清的欄位問題。原查詢寫 | json _ext="_ext"，只抽出了例外類型 _ext，後面卻寫 sum by (_ext, _msg)。以同一批實際 log 對照，指定欄位的解析只回傳 _ext label；改用 | json 才同時得到 _ext、_msg。因此現行查詢實際按例外類型計數，沒有再依訊息內容拆分。這是查詢結果的驗證，不代表線上規則已被修改。

Last 也有資料缺口要留意。某種 _ext 在一小時內曾有值，卻在最後幾個查詢點消失時，最後可用值未必代表評估當下的三十秒。or on() vector(0) 只在整體沒有匹配序列時補 0，不會替每個消失的 _ext 各補一個 0。遇到這種情況，應看 A 回傳的實際序列與 B 取出的值，再判讀觸發原因。

最後用一條每個列出的查詢點都有值的示意序列走完判斷。表中僅摘出 A 的幾個點，實際 A 在一小時內還會有其他點；評估假設剛好落在表中的時間，筆數不是線上歷史紀錄。
