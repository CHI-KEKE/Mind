一個選單，切換整張 Dashboard 的環境

環境變數集中保存資料來源名稱、namespace 與 service 的對照。Panel 引用同一組值，就能跟著環境選單一起切換。

環境對照如何流向 Panel

HK Prod 的設定流向
環境選單選擇 HK Prod
→
environment取得該環境的對照欄位
→
Panel使用對應資料來源與查詢條件
prometheusNameHK-Prod-Prometheus，交給 Cluster 選擇資料來源
namespaceprod-regular-purchase-service，代入 PromQL 的 namespace 條件
serviceprod-regular-purchase-service，代入 Loki 的 service 條件

建立新 Panel 時仍須引用 ${Cluster}、${environment.namespace} 或 ${environment.service}。各環境的實際值只在 environment 定義一次，不必為 TW、HK、MY 各複製一套 Panel。

六個環境共用一份欄位結構

TW / HK / MY Prod相同 namespace，不同資料來源

三個正式環境都使用 prod-regular-purchase-service，但各自指向不同市場的 Prometheus 與 Loki。

TW / HK / MY QA依環境挑選 namespace

QA 依市場使用不同 namespace；HK 與 MY 共用同名的 QA 資料來源。

環境名稱如何選到真正的資料來源

environment 保存名稱；Datasource variable 依名稱找到 Grafana 中已建立的連線。資料來源的連線設定與 Dashboard 的環境對照各有位置。

先有連線，再用變數挑選

Connections預先建立 HK-Prod-Prometheus 與 HK-Prod-Loki
→
environment提供 prometheusName 與 lokiName
→
Datasource variable依 Type 與 Name filter 選連線
→
Panel使用 Cluster 或 Loki

prometheusName 與 lokiName 是資料來源的名稱，不是連線位址。實際資料來源先在 Grafana 的 Connections → Data sources 建立。

兩道篩選條件

ClusterType：Prometheus

Name filter：^${environment.prometheusName}$

LokiType：Loki

Name filter：^${environment.lokiName}$

選擇 HK Prod 時，${environment.prometheusName} 展開為 HK-Prod-Prometheus。Cluster 先限制 Type 為 Prometheus，再以 Name filter 匹配這個既有資料來源。

Panel 最後引用哪個變數

PrometheusPanel 的 Data source 選 ${Cluster}
LokiPanel 的 Data source 選 ${Loki}

切換環境後，資料來源變數會依新名稱切換。cloudwatchName 也可按相同方式提供 CloudWatch 的名稱對照，但仍需另外建立並引用對應的 Datasource variable。

從第三方回應日誌畫出狀態碼趨勢

Payment Middleware 在收到第三方 HTTP 回應後寫入結構化日誌。Loki 將符合條件的日誌變成每分鐘筆數，Grafana 再依狀態碼畫線。

狀態碼從哪裡來

PMW 呼叫第三方例如 Stripe API
→
收到 HTTP 回應Handler 取得回應 StatusCode
→
寫入 MetricsLog記錄 Type、Host、Path、Status
→
Loki 保存日誌供 Panel 查詢

程式的 MetricsLogEntity.Type 固定為 Metrics。回應記錄 Handler 將第三方回應碼寫入 MetricsLog.Status；這是第三方呼叫的回應碼，不等於 PMW 對呼叫方回傳的狀態碼。

JSON 為什麼要解析

HK Prod 實際日誌的精簡欄位，識別資訊已省略 
{
  "_props": {
    "MetricsLog": {
      "Type": "Metrics",
      "Host": "api.stripe.com",
      "Path": "/v1/payment_intents",
      "Status": "402"
    }
  }
}
service 標籤{service=“$Namespace”} 先找出 PMW 日誌
JSON 解析| json 將巢狀欄位展開為 _props_MetricsLog_Type 與 _props_MetricsLog_Status
類型篩選Type = Metrics 只留下程式標記的統計紀錄

先計數，再合併相同狀態碼

模擬：同一分鐘內的三組日誌
Pod A / 20012 筆

一組標籤的計數

Pod B / 20018 筆

另一組標籤的計數

Pod A / 4021 筆

狀態碼不同，分開保留

Status 20012 + 18 = 30 筆
Status 4021 筆

count_over_time 先依原有日誌串流及解析出的標籤組合計數，並非語法指定按 Pod 計數。sum by (_props_MetricsLog_Status) 才忽略其他標籤，依狀態碼加總。

Time series Panel 的 LogQL 
sum by (_props_MetricsLog_Status) (
  count_over_time(
    {service="$Namespace"}
    | json
    | _props_MetricsLog_Type = `Metrics`
    [1m]
  )
)

每個點都往回看一分鐘

Query interval 若為 1 秒，圖表每秒算一個點；[1m] 則決定每個點都往回看一分鐘。相鄰兩個視窗約有 59 秒重疊。Panel 選 Time series、Query Type 選 Range，Legend 使用 {{_props_MetricsLog_Status}}。

所選時間內的第三方 4xx 有幾筆

這張 Stat Panel 只保留 4xx 的 MetricsLog，依 Dashboard 選擇的時間長度計數，最後顯示最新一個統計值。

篩選規則與時間長度

=~用正規表示式比對

可一次選出多種狀態碼；= 則只比對單一指定值。

(4)..以 4 開頭的三個字元

例如 402、404、429。更精確可寫 4[0-9]{2}。

[$__range]跟隨 Dashboard 時間長度

選 Last 6 hours 時展開成 [6h]。

第三方 4xx 統計 LogQL 
sum by (service) (
  count_over_time(
    {service="$Namespace"}
    | json
    | _props_MetricsLog_Type = `Metrics`
    | _props_MetricsLog_Status =~ `(4)..`
    [$__range]
  )
)

sum by (service) 將不同標籤組合的筆數合併，結果保留 service 名稱。這裡的 $Namespace 已選單一 service，因此最後通常只有一個數列。

Range 與 Last* 各負責什麼

Range 會在圖表範圍內反覆計算，每個點都往回看 $__range。Stat 的 Calculate → Last* 取最後一個非空值放大顯示，背景保留趨勢線；它不會把重疊視窗的各點再相加。

只需顯示所選時間內的最新總數時，可改用 Instant，直接在結束時間計算一次。保留 Range 是為了顯示背景趨勢；這條趨勢是滑動的區間總數，不是每個查詢間隔內的新事件數。

Ingress 請求數如何變成每秒速率

ingress-nginx 累積入口請求數，Prometheus 定期抓取樣本。PromQL 的 irate 再用最新兩筆樣本求出當下的增長速度。

監控程式部署在哪裡

HK Prod EKS Cluster
MonitoringPrometheus StatefulSet

維持 Prometheus Pod。它負責抓取、保存及查詢 metrics。

Payment MiddlewarePMW Deployment

維持 PMW Web API Pods。處理付款 API 請求。

Ingressingress-nginx Controller

處理入口流量並提供自身的 metrics endpoint。

Prometheus 是另外部署的應用程式，並非建立 EKS Cluster 時自動出現。StatefulSet 與 Deployment 都會依設定維持 Pods；StatefulSet 額外提供較穩定的 Pod 身分，資料持久性仍取決於儲存設定。

指標從產生到繪圖

請求進入 IngressController 更新累積計數
→
metrics endpoint提供 nginx_ingress_controller_requests
→
Prometheus定期以 HTTP 抓取並儲存樣本
→
Grafana送出 PromQL 並畫圖

nginx_ingress_controller_requests 是 ingress-nginx 定義的累積計數器，不是 PMW API 或 Grafana 自己命名的值。Prometheus 抓取的是 ingress-nginx 的 metrics endpoint，並非 PMW 的業務 API。

為什麼篩選 exported_namespace

namespaceingress-nginx，目前樣本中是被抓取的 Controller 所在 namespace
exported_namespaceprod-payment-middleware，指向這條請求指標所屬的 Ingress namespace

Prometheus 抓取時若遇到同名的 namespace 標籤，可能把原本指標的欄位改成 exported_namespace。這裡的兩個值已在 HK Prod 指標中觀察到；具體衝突設定仍需以該環境的 scrape 設定核對。

五筆樣本，irate 只用最後兩筆

以上是模擬樣本。[2m] 先限定搜尋最近兩分鐘的範圍；即使範圍內有五筆，irate 也只取最後兩筆：(116 − 110) ÷ 30 秒 = 0.2 次／秒。

Ingress request rate 的 PromQL 
sum(
  irate(
    nginx_ingress_controller_requests{
      exported_namespace="$Namespace"
    }[2m]
  )
) by (ingress)

sum … by (ingress) 將同一 Ingress 的不同 controller Pod、method 與 status 數列速率加總。這條查詢顯示每秒請求速率，沒有篩掉 4xx 或 5xx，也不是 PMW 對第三方的呼叫速率。
